# Ambiguous adjacent mutation slots are refused at compile time

Status: implementation specification. Tracking: [#54](https://github.com/zanminwang/axton/issues/54).

## 1. Problem

On the wire a mutation instance is `{name, version, operations: [{model, op, identity, values?}]}`; operations carry no slot name. The server (`decode` in `crates/server/src/lib.rs`) and the client's dependency derivation (`crates/client/src/policies.rs`) assign operations to slots by walking the slots in declaration order and matching `(model, op)`: a single slot takes one operation, an optional slot takes zero or one, a list slot takes every consecutive match.

When a slot of the same `(model, op)` follows a non-single slot with nothing fixed in between, the walk cannot tell the two apart:

```
mutation RemoveEntries { entries Entry.delete[]  maybe Entry.delete? }
```

`entries` consumes every `Entry.delete`, so `maybe` is never filled. With `first Entry.delete?  second Entry.delete`, a client that sends only `second`'s operation sees it assigned to `first` and `second` reported missing. The compiler accepts both shapes today.

## 2. Decision

The user decided on 2026-09-15: such declarations should not be supported. The compiler refuses them; the wire format and the decoders do not change.

**Rule.** For a mutation's slots in declaration order, a later slot `j` is *ambiguous* when an earlier slot `i` has the same `(model, operation)`, slot `i` is not single, and every slot strictly between `i` and `j` is not single. A single slot, of any `(model, operation)`, is a fixed position that separates what comes after it from what came before.

Consequences of the rule:

| Declaration | Verdict |
| --- | --- |
| `a A.delete[]  b A.delete?` | refused: `b` unreachable |
| `a A.delete?  b A.delete` | refused: `b`'s operation lands in `a` |
| `a A.delete  b A.delete?` | accepted: `a` is one fixed operation, `b` takes the next if present |
| `a A.delete  b A.delete` | accepted: positional |
| `a A.delete[]  x B.create  b A.delete?` | accepted: `x` separates them |
| `a A.delete[]  x B.create?  b A.delete?` | refused: when `x` is absent nothing separates `a` and `b` |
| `a A.delete[]  b A.update?` | accepted: different operation |

**Diagnostic.** The error is reported at the later slot's position, contains the phrase `ambiguous slot`, and names both slots: `ambiguous slot: maybe cannot be told apart from entries`. Same output convention as every other semantic error (`line:column: message`).

**Server and client decoders are unchanged.** Every schema the compiler now emits decodes deterministically under the existing greedy walk. The server does not add a descriptor check, because retained history versions (`backend.json` carries every retained version) may still contain the old ambiguous shape and must keep decoding exactly as they always did; refusing them at startup would break a deployed backend over a rule that only affects new declarations.

## 3. Fixture and history

`fixtures/compiler/example.model` declares the ambiguous `RemoveEntries` shape and its history fixture records it as version 1. Changing a slot at the same version is an incompatible input change, so the fixture moves to version 2:

```
mutation RemoveEntries { entries Entry.delete[] maybe Entry.update<note>? @deprecated(reason: "use entries") @@version(2) }
```

Version 1 stays in `fixtures/compiler/history/mutations.json` untouched. The generated-API fixtures under `integration/generated-api` are regenerated by `integration/generated-api/verify.sh`; hand-written files there that register `removeEntries` handlers gain a `v2` registration.
