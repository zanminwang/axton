# Client

## 1. Introduction and Goals

An application writes `client.mutations.addTodo(...)`, `client.queries.searchTodos(...)` and `client.models.todo.watch(...)` without seeing JSON or cursors. The client typed API consists of a generic runtime class per language and generated classes carrying the application's Model, Mutation and Query names and types.

## 3. Context and Scope

What an application sees:

| Surface | Purpose |
| --- | --- |
| `GeneratedClient.open({path, server?, connection?})` | open the local database; with `server`, connect and keep syncing |
| `client.models.<model>.get / query / watch / <relation>` | reads on the last commit; `watch` re-emits when results change |
| `client.mutations.<name>(args, options?)` | commit a durable Mutation intent and inferred Model optimism locally; return `Call<Output>` |
| `client.mutations.call.<name>(args, options?)` | execute a Mutation directly and return its final output |
| `client.queries.<name>(args, options?)` | execute a Query directly and return its final output |
| `client.queries.enqueue.<name>(args, options?)` | commit a durable Query intent with no optimism; return `Call<Output>` |
| `client.queries.<name>(args, { once, refresh, store })` | reuse, or save on success, the complete result of a direct Query ([#158](https://github.com/zanminwang/axton/issues/158)) |
| `client.queries.invalidate.<name>(args)` | discard the saved `once` results of one argument set, every store policy, in a local transaction |
| `client.transaction(tx => …)` with `tx.models.<model>.create / update / delete` | local reads and direct writes in one local transaction |
| `client.scopes.subscribe(scope)` | register durable intent to follow a Scope; answers the runtime's `Subscription` handle |
| `subscription.scope`, `.status`, `.watch(listener)`, `.unsubscribe()` | what one registration is, what it is doing, observation of its changes, and its durable removal |
| `client.channels.subscribe / unsubscribe` | the retained spelling of the same registrations |
| `client.syncState()`, `client.models.<model>.syncState(identity)` | the client's and one record's local sync state |
| `clientId`, `connect()`, `pendingTasks()`, `setReadiness()`, `runPrerequisites()`, `drop()`, `dismissRejection()`, `querySpec()`, `readSql()`, `close()` | identity, connection, recovery and escape hatches, on the same object |

Every call becomes one command through the [bindings](../bindings.md). Generated code depends on the runtime package (`@axton/client`, `package:axton`); the generic runtime depends on nothing generated.

The concrete generated client exposes standalone `client.models` local CRUD/read/watch, transaction `tx.models` local CRUD/read without watch or backend calls, and the `mutations` and `queries` namespaces. Each method fixes its delivery and return type; the four routes and their await boundaries are owned by [Mutations and Queries](../../schema/actions.md#3-context-and-scope). There is no `client.actions`. The generated methods use the SDK's shared types: TypeScript `Call`, `CallStatus`, `CallOutcome`, `CallError` and `CallOptions`; Dart `Call`, `CallStatus`, `CallOutcome`, `CallSuccess`, `CallFailure`, `CallError` and `CallStore`. No `mutations` or `queries` route may run inside an application-owned local transaction. Standalone local Model writes use their own local transaction and do not enqueue backend work.

**The subscription handle.** `subscribe` resolves when its local transaction commits: it awaits no authentication, connection or acknowledgement, so registering a Scope with no network is an ordinary offline write, and repeated calls for the same live registration answer the same cached handle, keyed by persistent subscription identity. `status` is one frozen snapshot with three parts, and `watch` delivers the current snapshot then every change until its returned function is called:

| Part | Values and meaning |
| --- | --- |
| `active` | whether this handle still names a live registration |
| `initialization` | `pending` until a durable starting boundary exists, then `ready`. It is a statement about committed state, not about the socket |
| `connection` | `offline` (no lane, or paused), `connecting` (no session, or one that has not covered this Scope yet), `catching-up` (a delta request is out), `live` (the session delivers normally - not that all history is loaded), `stopped` (the handle is closed) |

**A new subscription delivers from its origin, not from the beginning of the Scope** ([#150](https://github.com/zanminwang/axton/issues/150)): the first head the server acknowledges becomes its starting boundary, so records published before it are not loaded, and `live` says the stream is healthy rather than complete. Loading a Scope's existing records is the explicit `bootstrap()` operation of [#151](https://github.com/zanminwang/axton/issues/151). `unsubscribe()` commits the removal of that identity and stops the handle; repeating it is a no-op, and it cannot remove a later registration of the same Scope name. Other work through a closed handle fails with `subscription.closed` (`SubscriptionClosedException` in Dart). Closing the client stops every handle and cancels its observers, and deletes no subscription. A [rebuild](../../client/storage/reconciliation.md) replaces the replica with fresh registrations, so it stops every handle taken before it the way a removal does - `active` false, `connection` `stopped`, observers completed - and a later `unsubscribe()` through one of them is a harmless no-op. A Scope name that is empty or only whitespace names no Scope and is refused before anything is written, the same rule the socket's subscribe frame is held to. An observer's exception is reported through the host's uncaught-error channel after the commit, never turned into a transport failure or a rollback.

A durable call returns its handle after initial local acceptance and commit; that is not final backend success. The handle exposes only `status` and `wait()`, with `wait()` yielding either a result or a `CallError`. An initial local failure rejects before a handle exists. Only a durable Mutation derives optimism; a queued Query commits an intent with no Model operations. Direct calls skip the queue and automatic optimism, returning the result or rejecting with `CallError`; offline, they fail rather than enqueue. Each direct invocation takes a fresh call ID. A Model result is a per-invocation Loader snapshot: a later call in the same batch may change the batch-final settlement authority, and current local reads may include later optimism. Live handles keep business results in memory while pending/completion state remains durable.

All four routes take an optional `store` option beside the args ([protocol](../../protocol/actions.md#store-policy)). TypeScript generates `{Name}Options`, whose `store` is a boolean or a partial map restricted to the operation's explicit Model output names (boolean-only when there are none). Dart generates a `{Name}Store` selector with `all()`, `none()` and, when eligible outputs exist, `outputs(...)` with nullable booleans; the named parameter is `store`, or `outputStore` when a business input is already named `store`. The durable route validates and persists the policy with the call ID, args and optimism in one local transaction; the direct route validates it before dispatch.

## 5. Building Block View

- **Ports.** Read, write and live ports separate capabilities: a write port adds local direct writes to reads; a live port adds `watch`. A transaction implements the write port and cannot watch or invoke a Mutation or Query. [Generated code](../../compiler/generate.md) binds Model classes to these ports; `makeMutations` and `makeQueries` (TypeScript) and the Dart `Mutations`, `DirectMutations`, `Queries` and `QueuedQueries` classes bind operations to a `CallPort` through its existing `invokeAction` (durable) and `invokeDirectAction` (direct) members.
- **TypeScript hosts.** Node and React Native share [client orchestration](../../../../../packages/client-js/runtime.mts). Each entry point supplies its native string carrier, transaction scope, and server transport. Node retains AsyncLocalStorage savepoints; React Native uses an explicit transaction scope without a nested-savepoint API.
- **Client.** One promise chain per client serializes local commands, so calls from the application, the connection and watchers never interleave inside Rust. `transaction` sends `begin`, runs the body against a transaction object, then `finish` and `commit`, or `rollback` on any error. A durable call privately encloses inferred optimistic writes and enqueueing in one SQLite transaction, then returns a handle after commit. A direct call performs network I/O outside the long local database section and applies returned authority in a short transaction.
- **Transaction.** Commands are queued in submission order and marked as belonging to the transaction. `finish` fails if any command was never awaited, if any command failed even though the application caught the error, or if savepoints overlapped. `savepoint(body)` nests via async context (TypeScript) or zone values (Dart) so a failure inside it is confined to that scope.
- **Captured client guard.** A Mutation or Query call from its own active transaction callback fails before it can wait on the client's queue. Node uses async context and Dart a zone token to identify that callback. React Native rejects these calls while a public transaction is active; retry after the transaction settles. [Client runtime](../../../../../packages/client-js/runtime.mts) owns the shared guard and enqueue flow.
- **Watch.** Re-runs the query after every commit notification and emits only when the JSON result differs; Dart exposes a broadcast stream.
- **Generated code.** Types, codecs (dates to `Date`/`DateTime`), operation input/output bindings, Model classes and the two facades `GeneratedClient` and `GeneratedTransaction` ([Compiler / Generate](../../compiler/generate.md)). The client owns Mutations, Queries and watch; the transaction owns local Model reads and writes. Presence is expressed as an omitted key versus `null` in TypeScript and as `Present<T>?` in Dart; both encode to the same wire patch.

Code: [React Native adapter](../../../../../packages/client-react-native/index.ts), [shared runtime](../../../../../packages/client-js/runtime.mts), [client-js/index.mts](../../../../../packages/client-js/index.mts), [client-js/transaction.mts](../../../../../packages/client-js/transaction.mts), [dart/client.dart](../../../../../packages/dart/lib/src/client.dart), [dart/port.dart](../../../../../packages/dart/lib/src/port.dart).

## 9. Architecture Decisions

**One client object ([#133](https://github.com/zanminwang/axton/issues/133)).** The generated client is the application surface. It exposes `models`, `mutations`, `queries`, `scopes` and `channels` and carries runtime members directly; the runtime `Client` is an internal handle (`client.client`) used by framework tests. Operation-only and Model-only schemas do not emit an empty obsolete `mutate` facade. The per-record sync state lives beside `get` and `query` on each Model and is typed by its identity.

**Query once snapshots ([#158](https://github.com/zanminwang/axton/issues/158)).** `once` and `refresh` are invocation controls of the direct Query method only; no schema annotation selects them. Generated direct Query methods call the runtime's `invokeQuery` (TypeScript options `{Name}Options & OnceOptions`, in which `refresh` requires `once: true`; Dart named `once`/`refresh`, renamed `callOnce`/`callRefresh` when business inputs take those names), and `queries.invalidate` holds one typed invalidator per current Query (`invalidateQuery`, business args only; a Query may not be named `invalidate`). Mutation and `enqueue` methods keep store-only options; the TypeScript runtime also rejects once controls on them with `action.invalid_options`, while Dart's generic `invokeAction`/`invokeDirectAction` have no such parameters. Rust decides each call: a saved result (`Cached`), an active request of the same key and generation (`Join`) or a new direct request (`Fetch`). The runtime registers a fetched flight inside the same exclusive step that received the decision, so a later decision that joins it always finds it, executes the prepared body over the existing direct transport, finishes or fails the flight on every terminal path, and gives each caller its own parse of the raw outcome. The cached lookup precedes the direct-availability check, so a hit needs no connection. Keys, generations, fencing and the atomic save are the runtime's ([frontend interface](../../client/frontend-interface.md)).

**The Scope facade ([#150](https://github.com/zanminwang/axton/issues/150)).** `client.scopes.subscribe(scope)` is the current spelling and the generated `Scopes` class is a thin delegate: it forwards to the runtime's `subscribeScope`, which owns the handle, its immutable status and its observers ([client-js/subscriptions.mts](../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../packages/dart/lib/src/subscriptions.dart)). The generated module re-exports `Subscription` and `SubscriptionStatus` so application code can name what it gets back. The retained `channels` facade registers the same Scopes through the same ledger during this milestone, with no second cursor-zero path behind the old spelling; a get-only accessor is deliberately omitted from this first API, and [#152](https://github.com/zanminwang/axton/issues/152) owns removing the old names.

**Automatic model-version declaration ([#91](https://github.com/zanminwang/axton/issues/91)).** Generated client configuration identifies the [model versions](../../schema/models.md#9-architecture-decisions) expected by its generated types: the schema embedded in `generated.ts` and `generated.dart` carries each model's `version`, and `open` passes it to the Rust runtime unchanged. The runtime declares those read contracts to the server as `models` on every pull and on the subscribe frame ([Protocol / Pull](../../protocol/pull.md)); application code does not supply versions on each `channels.subscribe(...)` call. HTTP catch-up and WebSocket delivery must use the same selected contracts. This adds no protocol policy to the SDK: generated metadata passes through bindings to the runtime. Wire placement and validation remain to be designed; read-error behavior follows [failure isolation](../../server/engine/pull.md#9-architecture-decisions).

## 10. Quality Requirements

- **An unawaited or escaped call poisons the transaction, and a caught failure still rolls it back unless confined to a savepoint** (binding half of guarantee L3). Evidence: [transaction.test.mjs](../../../../../integration/bindings/client-js/transaction.test.mjs); [dart/test/client_test.dart](../../../../../packages/dart/test/client_test.dart) `Dart callbacks read their writes, rollback and reopen through native Rust`.
- **Generated code forwards calls unchanged and rejects misuse at compile time**. Evidence: [integration/generated-api/test.ts](../../../../../integration/generated-api/test.ts) (positives and `@ts-expect-error` negatives); [generated_test.dart](../../../../../integration/generated-api/generated_test.dart); the Scope facade's compile-time negatives in [negative/misuse.ts](../../../../../integration/generated-api/negative/misuse.ts) and [negative/misuse.dart](../../../../../integration/generated-api/negative/misuse.dart).
- **Generated Mutation and Query methods use the shared SDK handle types and preserve local Model writes and decoded result snapshots.** Evidence: [generated operation fixture](../../../../../integration/action-runtime-ts/verify.sh) and [mobile host adapter test](../../../../../integration/bindings/client-react-native/actions.test.mjs). The mobile test runs with the Node native library and mobile transaction adapter; it is not a device run.
- **Each of the four routes has its fixed return type in TypeScript and Dart, and misuse is a compile error.** Evidence: [types.ts](../../../../../integration/action-runtime-ts/types.ts); the positive and negative fixtures [positive.ts](../../../../../integration/action-contract/positive.ts), [negative.ts](../../../../../integration/action-contract/negative.ts), [positive.dart](../../../../../integration/action-contract/positive.dart) and [negative.dart](../../../../../integration/action-contract/negative.dart); [action-runtime-dart](../../../../../integration/action-runtime-dart/generated_test.dart).
- **Against a real backend: a default Query writes no queue row, a direct route does not enqueue offline, a queued Query survives reopen without optimism and reads when it executes, a direct Mutation resolves after its authority applies, and a same-ID retry replays.** Evidence: [client.test.mts](../../../../../integration/action-runtime-ts/client.test.mts) `generated routes resolve through the native pump and direct transport while Models stay local`, `every generated route forwards store options beside encoded args`; [action.test.mts](../../../../../integration/action-e2e/action.test.mts) `Queries read fresh on the direct route and at execution time when enqueued`, `a direct Query retry with the same call ID replays its saved result`, `a direct Mutation resolves after the backend commits and its authority applies`, `store selects which Search Query outputs update local Models on both routes`.
- **`once` reuses a complete result without a request or Model write, coalesces concurrent callers into one request, decodes independent results, works offline after reopen, keeps the snapshot on a failed refresh, and invalidation fences older requests; Mutation and `enqueue` routes refuse the controls.** Evidence: [query-once.test.mjs](../../../../../integration/bindings/client-js/query-once.test.mjs) (including a caller started at the moment the Fetch decision arrives), [client-react-native/query-once.test.mjs](../../../../../integration/bindings/client-react-native/query-once.test.mjs) (Node native library with the mobile transaction adapter; not a device run), [dart/test/query_once_test.dart](../../../../../packages/dart/test/query_once_test.dart); against a real backend with handler counts, [action.test.mts](../../../../../integration/action-e2e/action.test.mts) `once reuses the complete Query snapshot; default calls stay fresh; refresh replaces it`, `a hit returns the old snapshot while local Models move on, and writes or wakes nothing`, `once snapshots survive offline reopen; misses, refresh failures and invalidation behave`, `store variants are separate snapshots and store:false still persists the result`; generated types in the positive and negative [action-contract](../../../../../integration/action-contract/negative.ts) fixtures.
- **One handle per registration, offline registration, status from the committed boundary and the lane, a closed handle's `subscription.closed`, and client close versus unsubscribe.** Evidence: [subscriptions.test.mjs](../../../../../integration/bindings/client-js/subscriptions.test.mjs), [client-react-native/subscriptions.test.mjs](../../../../../integration/bindings/client-react-native/subscriptions.test.mjs) (Node native library with the mobile transaction adapter; not a device run), [dart/test/subscriptions_test.dart](../../../../../packages/dart/test/subscriptions_test.dart).
- **One end-to-end flow per language works against a real backend**. Evidence: [round-trip.test.mjs](../../../../../integration/e2e/round-trip.test.mjs).
- **Against a real backend: a new subscription's origin is the acknowledged head, nothing older is loaded, and that origin survives a reconnect and a reopen.** Evidence: [subscriptions.test.mjs](../../../../../integration/e2e/subscriptions.test.mjs).

## 11. Risks and Technical Debt

**Accepted limitation (planned change).** `watch` re-runs its query on every commit, whatever table changed; the binding already reports touched tables but neither client uses them, and there are no status streams. Scoped notifications are [#16](https://github.com/zanminwang/axton/issues/16).

**Accepted limitation.** `Client.open` and the generated `open` still accept a `migration` option that the runtime ignores; its future is part of [#20](https://github.com/zanminwang/axton/issues/20).

**To confirm.** No test runs one script through the Rust, TypeScript and Dart clients and compares state; the two clients are separate implementations of the same session logic ([Downlink worker](../../client/connection/controller/downlink-worker.md)), sharing the Rust engine alone does not establish equivalent behavior across SDK boundaries. The shared scenarios in `fixtures/scenarios` are prose READMEs, not an executable cross-language runner.
