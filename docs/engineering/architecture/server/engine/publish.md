# Publish

## 1. Introduction and Goals

Publish is how a change becomes visible to pull. Each Channel has a persistent set of member records. Settling a change gives the record a new position in every Channel it is a member of, at the record's current version, inside the same transaction as the change, and wakes live subscribers once that transaction commits. Publishing distributes a version; it does not create one.

## 3. Context and Scope

Application code declares two kinds of intent, synchronously, while a handler or an external callback runs ([Backend interface](../backend-interface.md#6-runtime-view)):

| Declaration | Meaning | Stamp | Positions |
| --- | --- | --- | --- |
| a Mutation input target (inferred) or `touch.todo(identity)` | the record changed | one new stamp per settlement, however many times it is declared | one in every Channel the record is finally a member of |
| `channel(name).todo.add(identity)`, `channel(name).add([Todo(identity), …])` | the record becomes a member of that Channel | an existing stamp is kept, a missing one is initialized at 1 | one in that Channel if the record was absent; nothing if it was already a member |
| `channel(name).todo.remove(identity)`, `channel(name).remove([…])` | the record stops being a member | unchanged | none; later changes no longer reach that Channel |

The same declarations exist in a Mutation handler (`ctx.channel`, `ctx.touch`), a legacy slot handler and `backend.transaction(async ({tx, channel, touch}) => …)`; a Query has neither. Membership is stored separately from the invalidation rows ([Persistence](../persistence.md)), outlives the callback, the subscribers and the backend process, and applies to a logical identity: a deleted record stays a member, so its Loader answers `null` there as a deletion, and a later record with the same identity is distributed to the same Channels. A settlement with no membership anywhere stamps its changes and publishes nothing. Each publication asks [Persistence](../persistence.md) to allocate the Channel's next *cursor* and upsert the invalidation row at the given stamp ([Pull](pull.md)). The set of Channels published in a transaction feeds the wake after commit ([Server / Connection / Controller](../connection/controller.md)).

## 5. Building Block View

- **Stamps and cursors are independent counters.** A stamp is per record and orders content; a cursor is per channel and orders pages. A change allocates one stamp; publishing it to channels A and B allocates one new cursor in each and carries that one stamp to both (guarantee D3). The simulation and the persistence tests hold this by construction: `publish` refuses a stamp that is not the record's current one.
- **Settlement order.** `settle_changes` reduces membership intents to the last one per Channel/record pair, guards every changed or membership record in canonical key order (`advanceStamp` for a changed record, `ensureStamp` for an unchanged one with a final add, `lockRecord` for a remove-only one) before reading its initial membership, then applies net membership changes and publishes, both in Channel then record order. A changed record reaches every Channel it is finally a member of; an unchanged record only the Channels it newly joined; each pair once. Only the final intent per pair counts, compared with the membership at settlement start: removing and re-adding a member, or adding and removing a non-member, changes nothing and publishes nothing. A record removed in the same settlement that changes it is not published to that Channel, which therefore sees no deletion either. The guards are an implementation detail, not version increments: `lockRecord` and `ensureStamp` never move a stamp.
- **Wake set.** The TypeScript session records every channel a `publish` host request passed through in the transaction, snapshots that set at each mutation's savepoint and restores it on rollback, so a rejected mutation's publications neither remain nor wake anyone. After the transaction commits, an in-process hub calls the wake callbacks registered by live sockets for those channels.

Code: shared settlement in [server/settlement.rs](../../../../../crates/server/src/settlement.rs) (`settle_changes`); the external path `settle_external` in [server/lib.rs](../../../../../crates/server/src/lib.rs); the declaration collector `createEffects` in [server/effects.mts](../../../../../packages/server/effects.mts); `transaction`, `Session.touched` and `WakeHub` in [server/index.mts](../../../../../packages/server/index.mts).

## 6. Runtime View

Inside a push or an operation call: handler runs, collecting changes and membership intents → settlement allocates the stamps, applies memberships and publishes → loaders read the input targets (and an operation's explicit Model outputs) back → receipt or result → commit → wakes. A retried call ID answers its saved outcome and settles nothing again. Outside a push with `backend.transaction`: the framework opens the application transaction → the body writes, collecting the same intents → the body returns → `settle_external` runs the same settlement, with no readback → completion check → commit → the framework wakes the touched channels.

## 9. Architecture Decisions

**External writes go through `backend.transaction` (decided in [#50](https://github.com/zanminwang/axton/issues/50), implemented 2026-09-15).** The framework owns the transaction, the completion check and the after-commit wake, so an application cannot publish without waking. Business writes and publications share one transaction; a failure rolls back both and wakes nobody. Cross-process wakes stay with [#62](https://github.com/zanminwang/axton/issues/62). Evidence: [runtime.test.mjs](../../../../../integration/persistence/server/runtime.test.mjs) `backend.transaction publishes in the application transaction and wakes after commit`, `backend.transaction rolls back a failing body and wakes nobody`, `backend.transaction wakes a connected live subscriber without reconnect`.

**External writes speak the handler vocabulary ([#132](https://github.com/zanminwang/axton/issues/132), 2026-09-16).** The body of `backend.transaction` receives the declaration handles a handler receives, and the engine settles them after the body returns through `settle_external`, the same settlement without a load step. The separate `notify` vocabulary, its bound-session variant `bindTransaction(tx).notify` and the `publish(changes, channels)` engine entry are gone: one way to report a change, whether or not a client uploaded it. Evidence: [server/tests/stamp.rs](../../../../../crates/server/tests/stamp.rs) `an_external_settlement_advances_one_stamp_per_record_and_distributes_it_at_that_stamp`; [runtime.test.mjs](../../../../../integration/persistence/server/runtime.test.mjs) `re-adding an unchanged member keeps its stamp and publishes nothing; a later touch reaches its Channel without another add`, `notify and bindTransaction are gone; backend.transaction is the only external write path`.

**Persistent membership replaces per-call publication ([#140](https://github.com/zanminwang/axton/issues/140), 2026-09-26).** A handler used to publish its change set to named Channels on every call (`publish({channel})`), so a record reached only the Channels the latest writer remembered. Membership is now a stored relationship declared once (`channel(name).todo.add`), and every later change of the record reaches all its Channels, whoever writes it. Changes (`touch`, inferred inputs) and membership are separate declarations: adding does not change a record, and touching does not enroll it. One settlement algorithm, `settle_changes`, serves operation handlers, legacy slot handlers and external transactions. There is no publish-all fallback and no membership inferred from historical invalidation rows: an existing development database starts with an empty membership table and its fixtures re-enroll explicitly. Evidence: [server/tests/membership.rs](../../../../../crates/server/tests/membership.rs) `a_changed_member_advances_once_and_gets_one_new_position_per_channel`, `a_newly_added_changed_record_gets_one_position_at_its_final_stamp`, `membership_operations_that_cancel_change_nothing_and_publish_nothing`, `a_removal_is_net_and_a_record_removed_while_changed_is_not_published_there`, `legacy_and_external_paths_share_the_settlement`, `settlement_guards_records_in_key_order_then_writes_in_channel_order`.

## 10. Quality Requirements

- **A change allocates one stamp per settlement and every Channel it is a member of receives it once at that stamp; adding an unchanged record initializes a missing stamp and otherwise reuses it; output-only reads and an unchanged add move no stamp; a publication naming a stale stamp is refused** (guarantee D3). Evidence: [server/tests/membership.rs](../../../../../crates/server/tests/membership.rs) `a_changed_member_advances_once_and_gets_one_new_position_per_channel`, `output_only_reads_and_unchanged_enrollment_keep_the_existing_stamp`; [server/tests/stamp.rs](../../../../../crates/server/tests/stamp.rs) `an_external_settlement_advances_one_stamp_per_record_and_distributes_it_at_that_stamp`; [server/tests/actions.rs](../../../../../crates/server/tests/actions.rs) `a_duplicate_or_inferred_touch_allocates_one_stamp`; [server/tests/readback.rs](../../../../../crates/server/tests/readback.rs) `enrolled_changes_publish_at_their_allocated_stamps`, `a_change_without_membership_publishes_nothing`, `a_publish_that_echoes_another_stamp_is_host_invalid`; the PostgreSQL stamp and membership regressions under [Persistence](../persistence.md#10-quality-requirements).
- **Concurrent touch, add and remove serialize on the record row, so the enrolled Channel always holds the final stamp and a removed Channel receives nothing later; membership-only races keep the stamp.** Evidence: [membership.test.mjs](../../../../../integration/persistence/server/membership.test.mjs) `touch and add serialize in either order: the enrolled Channel always holds the final stamp`, `touch and remove serialize in either order; the stale touch retries and publishes nothing to the removed Channel`, `membership-only races keep the stamp; a duplicate add publishes once; a remove of an absent record orders before a first enrollment`.
- **A rejected mutation or a rolled-back transaction publishes nothing and changes no membership; a saved call replays without restamping, republishing or re-enrolling.** Evidence: `rejected mutation publishes nothing even though it declared a membership first`, `declarations roll back with the user transaction, and an unknown Model is refused at the declaration`; [membership.test.mjs](../../../../../integration/persistence/server/membership.test.mjs) `a call rejected after settlement rolls back its writes, relationships, stamps, heads and wake; the batch continues`, `a failed transaction rolls back every table, the saved outcome and the wake; the retried batch settles once`; [server/tests/membership.rs](../../../../../crates/server/tests/membership.rs) `a_saved_call_replays_without_restamping_republishing_or_re_enrolling`.
- **Subscribers are woken only after commit, and never by a duplicate receipt.** Evidence: `live transport negotiates, wakes only after commit, reconnects, and cleans up`.

## 11. Risks and Technical Debt

**Accepted limitation.** Wakes are in-process: a second server instance, or a publication from another process, does not wake this process's sockets; those clients catch up on reconnect. Cross-process notification delivery is [#62](https://github.com/zanminwang/axton/issues/62).

**Potential risk.** Every publication to a channel updates the same channel row under a row lock, so handlers touching one hot channel serialize and may retry on serialization failure; every change to a record locks its stamp row the same way. Not measured ([#12](https://github.com/zanminwang/axton/issues/12)).

**Accepted cost.** Settlement runs before the input readback, so a Mutation that its Loader or a version check later refuses has already taken its stamp, membership and Channel-head writes when the savepoint rolls them back. Under concurrency those extra row writes can add serialization retries of the whole application transaction (bounded, as before). Not measured.
