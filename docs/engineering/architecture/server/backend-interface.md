# Backend interface

## 1. Introduction and Goals

The backend interface is where the framework meets application code. The Rust engine never touches the application's database directly; instead it asks a *host* to do things, and the host runs each request inside the transaction the application opened. Two of those requests reach application code: run this handler, load these records.

## 3. Context and Scope

**Operation host contract.** The generated backend registers one handler for each retained Mutation or Query version, under `mutations` or `queries` by that version's kind. The host invokes it with `{ctx, args}`: a Mutation's `ctx` contains the application transaction, authenticated user, stable call ID, `touch` and `channel(name)` (section 6); a Query's `ctx` contains only the transaction, user and call ID, and the host answers its `handle` with empty changes and memberships. `args` is decoded from the retained input snapshot. The handler returns explicit scalar/enum values and identity objects for explicit Model outputs, and nothing else: no output is inferred from an input, whatever its name. The shared executor refuses a Query settlement carrying changes or memberships with `query.effects_forbidden` whatever host produced it, before any stamp, readback or publication ([enforcement and its limit](../schema/actions.md#8-crosscutting-concepts)). It resolves Model outputs through the appropriate retained Loader version. The handler's output snapshot is distinct from the batch-final input readback. See [server execution](engine/README.md) and [typed server API](../sdks/typed-api/server.md).

`CallRejected(code)` is the public backend business-rejection class for both kinds; it has the same explicit code semantics as the retained legacy `MutationRejected` path described below. A handler or Loader exception that is not a business rejection becomes `handler.failed` or `loader.failed` for that call unless it is a retryable database transaction error. A persistence fault aborts the outer transaction for retry. Diagnostic callback exceptions after commit are reported through the SDK runtime uncaught-error channel and cannot replace the committed outcome.

The host operations the engine may issue:

| Operation | Answered by | Purpose |
| --- | --- | --- |
| `handle` | the application's handler | run one mutation's business logic |
| `load` | the application's loader | return the current state of records |
| `savepoint`, `rollback`, `release` | [Persistence](persistence.md) | isolate one mutation's effects |
| `claim`, `saveReceipt`, `head`, `scan` | [Persistence](persistence.md) | client rows, receipts and the invalidation table |
| `advanceStamp`, `ensureStamp`, `publish` | [Persistence](persistence.md) | record stamps and channel cursors ([Publish](engine/publish.md)) |
| `lockRecord`, `memberships`, `setMembership` | [Persistence](persistence.md) | record guards and persistent Channel membership |

Each operation is one variant of `HostRequest` with one response type, defined once in [server/host.rs](../../../../crates/server/src/host.rs) and restated for TypeScript in [server/host-contract.mts](../../../../packages/server/host-contract.mts) (section 9). [fixtures/protocol/host-operations.json](../../../../fixtures/protocol/host-operations.json) carries one example of every request and every response variant, and both hosts are tested against it.

Application-facing contracts ([Typed API / Server](../sdks/typed-api/server.md) shows their types):

- A legacy slot **handler** receives `{input, tx, userId, channel, touch}`: the decoded input (one value per slot), the transaction, the user id and the same declaration handles an operation handler has. The records the uploaded operations target are already the mutation's changes; `touch.todo(identity)` reports a record the handler changed beyond them, and `channel(name).todo.add(identity)` / `.remove(identity)` change persistent membership. Its return value is ignored. Throwing `MutationRejected`, or an error `translateRejection` maps to a code, rejects that one mutation; any other error rejects that same mutation with `handler.failed` and is reported to `onError` — the rest of the batch still runs and commits ([#95](https://github.com/zanminwang/axton/issues/95)). What the framework does with the change set after the handler returns is [Push](engine/push.md).
- A **loader** serves one retained model read contract (a model name and version) and receives `{ids, tx, userId}`: identities, the transaction and the user id, never a channel. It returns one row or `null` per identity, in order, shaped as that version's records. `null` means "not visible or deleted" and is delivered as a delete; a missing entry or `undefined` is a defect. Throwing `MutationRejected` (or an error `translateRejection` maps) refuses the read; any other error is a failure and is reported to `onError`. Inside a push either rejects the mutation being read back (with the refusal code, or `loader.failed`); in a pull either becomes that record's `error` change and the rest of the page is served ([Server / Engine / Pull](engine/pull.md)). Without an `onError` option, errors are logged with `console.error`.
- `authenticate(request)` returns the user id or null. Handlers and loaders own application authorization; the framework does not enforce channel-level policy ([#22](https://github.com/zanminwang/axton/issues/22)).
- The application also owns unique and identity constraints on the server, child deletion (`onTargetDelete` is a client-side cascade), and one local database per signed-in user; the backend is TypeScript on Node only, and prerequisite arguments are `self` only. These accepted limits are stated for authors in [What your backend owns](../../../../website/docs/backend/api.md#what-your-backend-owns).

## 5. Building Block View

Startup validates the compiled config and requires a handler for every retained version of a slot mutation (under `handlers`) or an operation (under `mutations` or `queries`, by that version's kind) and a loader for every retained model version; a missing, extra or wrong-kind registration makes `createBackend` throw. The engine decodes the config's `models` list (every retained model read contract, `{name, version, identity, fields, enums}`) into one normalization schema per version, refusing a contract whose identity differs from the model's, a duplicate version, an invalid field or enum, and a schema whose current version is not retained; a hand-written config without `models` retains each model at the schema's own version. A mutation's handler key and a model's loader key are `lowerFirst(name)`; each value holds a `v<n>` member per retained version, and a contract retaining only v1 also accepts the bare function ([Typed API / Server](../sdks/typed-api/server.md#9-architecture-decisions)).

At runtime the host function shapes handler input from the engine's decoded arguments: a create slot becomes `{…identity, …data}`, an update becomes `{identity, patch}`, a delete becomes `{identity}`; list slots are arrays and optional slots may be `null`. These are plain data: a declaration takes the record itself for a create and `input.todo.identity` otherwise, and copies only the identity fields.

A per-transaction **session** tracks every host callback promise. It records the first failure, refuses to let the transaction commit while callbacks are unfinished or failed, and snapshots the set of channels published to around each mutation's savepoint so a rejected mutation wakes nobody ([Publish](engine/publish.md)). `backend.transaction` runs application code outside a push on the same machinery, with `settle_external` in place of `handle` and `load` ([Publish](engine/publish.md)).

Code: the operation contract in [server/host.rs](../../../../crates/server/src/host.rs) (`HostRequest`, the response types, `HostExt::call_typed`) and the `Host` trait in [server/lib.rs](../../../../crates/server/src/lib.rs); on the TypeScript side the same contract in [server/host-contract.mts](../../../../packages/server/host-contract.mts) and `createBackend`, `host`, `Session` in [server/index.mts](../../../../packages/server/index.mts), with the persistence half answered by [packages/postgres/src/persistence.mts](../../../../packages/postgres/src/persistence.mts) over a two-method driver ([Persistence](persistence.md)). The simulation implements the same operations in memory in [crates/sim/src/host.rs](../../../../crates/sim/src/host.rs).

## 6. Runtime View

**Collecting declarations.** While a handler or a `backend.transaction` body runs, `touch`, `channel(name).todo.add/remove` and the mixed `channel(name).add/remove([Todo(identity), …])` only record intent. Each call is synchronous, returns nothing, validates its Channel name and identities, and copies the identity fields at that moment, so later mutation of the passed object cannot retarget it; a mixed call validates every reference before recording any, so a caught error leaves nothing half-declared. The handles close when the callback settles, including when it throws, and an escaped handle refuses later use. The host then answers `handle` with `{changes, memberships}` (plus `outputs` for an operation): the touched records, deduplicated after the inferred targets, and the membership intents in call order. The engine settles them first and then reads the input targets back through `load` ([Push](engine/push.md), [Publish](engine/publish.md)); membership fan-out happens in Rust, never in an SDK loop. A handler that declares nothing is a normal success: its input targets are still stamped and read back and the receipt still carries them. Returning from the handler commits nothing: settlement or a read can still reject the call and roll its declarations back.

**Rejection versus failure.** `handle` and `load` each answer one of three things: a rejection (a value: `{rejection}`), a failure (also a value: `{error}`, what the TypeScript host answers for a thrown handler or loader error that is neither `MutationRejected` nor a `translateRejection` code), or a thrown error that crosses the host boundary itself. A rejection and a failure both roll back only that mutation's savepoint and continue with the next: `handler.failed` and `loader.failed` are the engine's codes for a handler's or a loader's `Failed` answer, and the host has already passed the underlying error to `onError`. Only a thrown error — a persistence fault, or a host too old to answer `Failed` — propagates out of the callback and fails the outer transaction, so the whole batch, its publications and the client row roll back together; this is infrastructure, not a business outcome (guarantees P6, P7). Loaders follow the same three-way rule. A refusal or a `Failed` answer is the mutation's rejection in a push, and in a pull the engine retries the batched load one identity at a time so that exactly the failing records become `error` changes. A defective result (misaligned, malformed, `undefined`) still aborts the pull rather than advancing the client's cursor past bad data.

## 9. Architecture Decisions

### One typed host-operation contract, owned by Rust ([#45](https://github.com/zanminwang/axton/issues/45))

**Decision.** The Rust server crate becomes the single definition of every host operation: a `HostRequest` enum and one response type per operation, serialized to the JSON the boundary already carries. The TypeScript host, the simulation host and the test hosts implement that definition; none of them interprets free-form `{op, …}` objects any more. No wire protocol changes, business logic stays in handlers and loaders, and transaction ownership stays with the application.

**Contract (Rust, `crates/server/src/host.rs`).**

| Request (`op`) | Fields | Response type |
| --- | --- | --- |
| `claim` | `owner`, `clientId` | `Claimed { clientId, owner, sequence, receipt: Option<String> }` |
| `saveReceipt` | `owner`, `clientId`, `sequence`, `receipt` | unit |
| `head` | `channel` | `u64` |
| `scan` | `channel`, `after`, `limit` | `Vec<Invalidation { channel, cursor, model, identity, identityKey, stamp }>`, `stamp` being the record's current stamp |
| `savepoint` / `rollback` / `release` | `ordinal` | unit |
| `handle` | `name`, `version`, `arguments`, `owner`, `ordinal` | `Handled::Settled { changes: Vec<RecordRef>, memberships: Vec<MembershipIntent { channel, model, identity, present }> }`, `Handled::Rejected { rejection }`, or `Handled::Failed { error: String }`; `handleAction` answers the same with `outputs` beside `changes` and `memberships` |
| `load` | `model`, `version`, `identities`, `owner` | `Loaded::Rows(Vec<Option<Value>>)` (one entry per identity), `Loaded::Refused { rejection }`, or `Loaded::Failed { error: String }` |
| `advanceStamp` | `model`, `identityKey` | `Stamped(u64)`: the record's next stamp, 1 for a record without one |
| `ensureStamp` | `model`, `identityKey` | `Stamped(u64)`: the record's current stamp, initialized at 1 only when it has none |
| `publish` | `channel`, `model`, `identity`, `identityKey`, `stamp` | `Published { cursor, stamp }`; refused unless `stamp` is the record's current one |
| `lockRecord` | `model`, `identityKey` | `Locked = Option<Stamped>`: the unchanged stamp, `null` when the record has no row |
| `memberships` | `model`, `identityKey` | `Memberships(BTreeSet<String>)`: unique Channel names valid under `check_channel`, held in byte order |
| `setMembership` | `channel` (valid under `check_channel`), `model`, `identityKey`, `present: bool` | unit |

`HostRequest` derives `Serialize`/`Deserialize` with `#[serde(tag = "op", rename_all = "camelCase", rename_all_fields = "camelCase")]` and `deny_unknown_fields`; each response is a struct or enum with `deny_unknown_fields`. The engine constructs requests as enum values and decodes responses into these types, so a malformed response fails at the boundary, naming the operation and the offending field, instead of somewhere later with `unwrap`.

The code it fails with is the one that operation already used (`invalid_code` in `host.rs`), so no refusal changes its code:

| Code | Operations |
| --- | --- |
| `storage.invalid` | `claim`, `saveReceipt`, `scan` |
| `handler.invalid` | `handle` |
| `loader.invalid` | `load` (a malformed answer) |
| `host.invalid` | `head`, `savepoint`, `rollback`, `release`, `advanceStamp`, `ensureStamp`, `publish`, `lockRecord`, `memberships`, `setMembership` |

**How each side consumes it.**

- *Rust engine.* `process_push`, `read_back`, `process_pull`, `publish` and `live` build `HostRequest` values; a small `Host` extension (`call_typed<R: DeserializeOwned>(&self, request: HostRequest) -> Result<R>`) does the serialize/deserialize once. `Host::call` keeps its `Value → HostResult<Value>` shape so existing implementers compile during the migration.
- *TypeScript host.* `packages/server/host-contract.mts` declares the request and response types (one `type HostRequest = …` union and the response interfaces) and `packages/server/index.mts` narrows on `request.op` with an exhaustive `switch`; `packages/postgres` answers the persistence half against the same types, through its driver. The file is hand-written, because the two languages have no shared code generator today.
- *Conformance fixture.* A Rust test serializes one example of every request and one valid response per operation into `fixtures/protocol/host-operations.json`. Rust checks that every request decodes back to the enum and every response into its type; a Node test feeds each request through the TypeScript host with a fake persistence and compares the answers, in JavaScript, against the responses the same fixture records (in the persistence suite). A field added on one side without the other fails one of the two.
- *Simulation and test hosts.* `MemHost` and the `Fixed` test host match on `HostRequest` (deserialized from the `Value` they receive) and return the response types serialized, so an unknown or malformed operation is a compile error in Rust rather than an `unwrap` in a match arm.

**Consequences.** Adding an operation or a field means editing `host.rs`, the fixture and `host-contract.mts`; the Rust compiler and the two conformance tests enforce the rest. The boundary keeps JSON strings, so no binding change is needed.

Three answers a host could get away with before are now refused. Each keeps its operation's code and the abort semantics that code already had:

- A response carrying fields beyond the contract is refused (`deny_unknown_fields`), where the extra fields used to be ignored.
- `saveReceipt`, `savepoint`, `rollback` and `release` must answer exactly `null`, which is what every host already returns.
- A `handle` answer carrying `changes` or `memberships` beside `rejection`, or only one of `changes` and `memberships`, is refused with `handler.invalid` ("invalid handler settlement"), as is a change or membership without a model or an object identity, a membership without a Channel or a boolean `present`, and the retired `publications` field. A `load` answer that is neither a row list, `{rejection}` with a valid code, nor `{error}` is `loader.invalid`.

**Migration steps.** Each step was independently shippable and kept every existing test green; all four have landed.

1. Add `host.rs` with the types, `call_typed`, and the round-trip fixture test; switch the engine's call sites to build `HostRequest` and decode responses. No host implementation changes yet.
2. Switch `MemHost` and the server test hosts to match on the decoded enum.
3. Add `host-contract.mts`, narrow the TypeScript host and the Prisma persistence on it, and add the Node conformance test over the fixture.
4. Update this document's §3 table and the code map to point at `host.rs` and `host-contract.mts`; remove the §11 debt entry.

**Validation plan.** `cargo test -p axton-server -p axton-sim --locked` for steps 1–2 (round trip, refusals of malformed responses per operation, unchanged sim scenarios); `bash integration/persistence/server/run.sh` for step 3 (the whole existing suite plus the conformance test); `npm run typecheck`.

## 10. Quality Requirements

- **The host answers `handle` with the changes and the membership intents, a rejection, or a failure, never more than one of the three; `load` answers rows, a refusal, or a failure; every operation round-trips through the fixture on both sides.** Evidence: [server/tests/host_contract.rs](../../../../crates/server/tests/host_contract.rs) `the_operation_list_matches_the_request_enum`, `the_fixture_covers_every_operation_exactly_once`, `every_fixture_request_and_response_round_trips`, `a_handle_response_carries_changes_and_memberships_or_a_rejection_and_never_both`, `a_load_response_is_rows_or_a_refusal_code`, `a_response_of_the_wrong_type_is_refused_per_operation`; [host-contract.test.mjs](../../../../integration/persistence/server/host-contract.test.mjs) `the fixture and the TypeScript union cover the same operations`, `every fixture request replays through the TypeScript host to the fixture answer`, `the same handle request settles as the fixture rejection when the handler refuses`.
- **A handler that declares no membership still succeeds with readback records; a touched extra record added to a Channel is delivered there but is not caller authority; an added record is not a changed one; `channel(name)`, `touch` and the membership writers validate at the call; a handler may keep writing after a declaration; slot arguments are plain data and a handler's declaration handles close when it settles.** Evidence: [runtime.test.mjs](../../../../integration/persistence/server/runtime.test.mjs) `a handler that declares no membership still returns readback records and touches no channel`, `a touched extra record added to a Channel is settled and delivered there, but is not caller authority`, `an added record is not a changed one: it is initialised at stamp 1 once, and re-adding a member publishes nothing`, `a declaration validates its Channel and records at the call; the invalid call rejects only that mutation as a failure`, `a handler may keep using the transaction after a declaration; the membership settles with the commit`, `slot arguments are plain data; a handler declares with their identity, and its handles close when it settles`; the collector itself in [effects.test.mjs](../../../../integration/persistence/server/effects.test.mjs).
- **A rejection or a `Failed` answer rolls back only its mutation, with `handler.failed`/`loader.failed` for the latter; a loader refusal in a push does the same; any other thrown error rolls back the batch** (guarantees P6, P7). Evidence: [readback.rs](../../../../crates/server/tests/readback.rs) `a_handler_failure_rejects_only_that_mutation`, `a_loader_failure_rejects_only_that_mutation`, `a_failed_rollback_fails_the_delivery`; `explicit rejection rolls back only mutation and its publication`, `a loader refusal during push rejects only that mutation; so does a thrown loader error`, `registered translator rejects one mutation; malformed translator code aborts transaction`; [runtime.test.mjs](../../../../integration/persistence/server/runtime.test.mjs) `a handler that throws rejects only its mutation and reaches onError`, `a handler whose SQL fails leaves an aborted transaction that the savepoint rollback recovers into one rejection`, `a loader that throws during readback rejects only that mutation`, `a handler that breaks the transaction still fails the delivery`.
- **In a pull a refused, failed or malformed read is that record's `error` change and never aborts the page; `null` is a delete, `undefined` is a failure, never a delete; loaders receive no channel; `onError` defaults to `console.error`.** Evidence: `a loader that throws for one id fails only that record and reaches onError`, `a loader refusal for one id is an error change carrying the refusal code`, `loader defects fail only their records; the page is served and the cursor advances`, `an undefined loader entry fails only its record, reaches onError and never becomes a tombstone`, `loaders receive no channel`, `onError defaults to console.error so nothing is dropped silently`.
- **Unawaited or failed callbacks prevent commit.** Evidence: `pending unawaited publication prevents outer transaction commit`, `external transaction binding retains swallowed publication failure until its completion gate`.
- **Arguments decode known fields and ignore unknown ones; disallowed patches and binding mismatches have stable codes.** Evidence: [server/tests/runtime.rs](../../../../crates/server/tests/runtime.rs).

## 11. Risks and Technical Debt

**Resolved: the host operation set was an untyped string contract implemented three times.** Section 9 landed ([#45](https://github.com/zanminwang/axton/issues/45)): `host.rs` is the one definition, `host-contract.mts` restates it for TypeScript, and the shared fixture fails whichever side drifts. What remains is the hand-written mirror — the two languages have no shared generator, so adding an operation still means editing `host.rs`, `host-contract.mts` and the fixture; the compiler and the two conformance tests catch a half-done edit, they do not spare it.

**The contract grew with readback ([#55](https://github.com/zanminwang/axton/issues/55)) and with failure isolation ([#95](https://github.com/zanminwang/axton/issues/95)).** `load` gained `version` for model read contracts ([#91](https://github.com/zanminwang/axton/issues/91)) and lost `channel`; `handle` answers a change set and membership intents instead of a channel ([#140](https://github.com/zanminwang/axton/issues/140) replaced its former publications); `advanceStamp` and `ensureStamp` are new and `publish` takes the stamp instead of allocating one; `load` may answer a refusal. `#95` (mutation half) added the third `Failed { error }` answer to both `handle` and `load`, so the TypeScript host can report a thrown application error as data instead of letting it abort the delivery; a host that still throws is treated as infrastructure, as before. Every operation has one example in the fixture. The read half of `#95` uses the same answers on pull pages, isolated per record.

**Accepted limitation.** A loader must return exactly its version's contract fields: identity fields may be present, an absent nullable field reads as `null`, an absent non-nullable field or any extra property fails normalization: in a pull that record is a `loader.invalid` change, in a push that mutation is rejected with `loader.invalid`, and either way the host reports it to `onError`. Evidence: `normalize_state` over the retained contract in `process_pull`; the loader-defect test above and `a pull reaches the loader of the declared model version and normalizes rows with that contract`. Documented for authors under [Loaders](../../../../website/docs/backend/api.md#loaders).
