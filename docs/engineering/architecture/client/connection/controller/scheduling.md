# Scheduling

## 1. Introduction and Goals

Scheduling answers one question per lane: should the lane run a cycle now, wait, or stay idle? Putting that decision in Rust keeps retry policy identical across languages. The client [runtime](../../runtime.md) asks the question, turns a wait into a `timer` effect and a cycle into `http` or `socket` effects; the host only runs those effects on its platform's timers and network.

## 3. Context and Scope

Interface to Rust for the push lane: the `ConnectionDriver` controls `start`, `stop`, `pause`, `resume`, `wake`, `complete(success)`, and the query `next` → `idle` | `sync` | `wait {millis}`, called by the runtime's push lane ([client/runtime/lanes.rs](../../../../../../crates/client/src/runtime/lanes.rs)). The downlink lane embeds the same driver in `DownlinkWorker`: the runtime feeds it the same controls and executes the `wait {millis}` among its actions ([Downlink worker](downlink-worker.md)). Interface to the application: `Client.connect(server, {onError, refreshAuth})` submits a `connect` task and answers `{pause, resume, wake, close}`, each a `connection` task ([Bindings](../../../sdks/bindings.md)).

## 5. Building Block View

The Rust `ConnectionDriver` holds six fields: running, paused, dirty, in flight, attempt count and the time the next attempt is due. `next` returns `sync` only when the lane is running, not paused, has nothing in flight and is dirty; `wait` while a retry is due in the future; `idle` otherwise. A successful completion clears the attempt count and leaves the lane clean; a failure marks it dirty and schedules the next attempt at 250 ms doubling per attempt, capped at 30 s, with ±20 % jitter from the entropy the runtime is given. `wake` marks the lane dirty without interrupting a cycle in flight. `restart`, used by the Downlink worker after a replica rebuild, keeps running and paused, forgets the attempt in flight and its backoff, and leaves a running lane dirty and due at once ([Downlink worker](downlink-worker.md)).

The downlink lane applies the same policy to its second work class: a Bootstrap page is scheduled only while the lane is started and not paused, a transport failure defers the next page by the same bounded backoff, and a `resume` clears the deferral. That schedule is independent of the session's - a load is not retried by reopening a socket, and a socket is not reopened by a failed load - and it has no overall timeout, because waiting for connectivity is not a failure ([Downlink worker](downlink-worker.md)).

The runtime drives both lanes as lane units, interleaved with foreground tasks in arrival order ([Runtime](../../runtime.md#6-runtime-view)). A lane is looked at again when it is marked dirty: by a control, by a task or continuation that committed, by an effect result, or by its `timer` effect firing; marking it dirty also cancels the timer it slept on. Because those flags are set by the runtime's own units, no wake can fall between a decision and a sleep. The difference between the lanes is the body: the push lane runs one cycle when told to sync and reports its outcome to the driver; the downlink lane pumps the worker and executes the actions it answers, and pumps again while actions come back ([Downlink worker](downlink-worker.md)).

## 6. Runtime View

`pause` cancels the lane's I/O - the push in flight, the socket, its catch-ups and the historical page in flight, which belongs to the lane rather than to the socket - with `cancelEffect`, and pauses both drivers. The abandonment is the lane's own, so it is not reported to the application and schedules no backoff: the driver completes the abandoned push as a success, and the worker is still told that its historical page `failed`, with no status, which is how it clears its slot; `resume` clears the deferral and the page is asked for again. While paused no request of either kind starts, and an answer the runtime had already admitted is still applied: it is local work with no I/O, and its records are stamp-idempotent ([Downlink worker](downlink-worker.md)). `resume` clears the pause and marks the lanes dirty. `stop` abandons what `pause` does, cancels a credential refresh in flight, fails direct calls still waiting on the network with `action.unavailable` and ends the connection; controls after it are no-ops, and the SDK's closed connection object sends none, so a stale handle cannot affect a replacement.

On failure the runtime reports it - a `report` with the message and the HTTP status the host's effect result carried - and the SDK hands it to `onError`. If the failure was a 401 and the application supplied `refreshAuth`, the runtime asks for one `refreshAuth` effect before the push lane's failure is counted or the worker hears `closed` or `failed`; every 401 that arrives while it runs, on either lane or on a direct call, waits for the same refresh. A `failed` event carries the HTTP status, because a Bootstrap run is failed by a refusal the server decided and retried after anything else.

## 10. Quality Requirements

- **Backoff is bounded and a wake never busy-loops; the lanes are looked at again on their own timers.** Evidence: unit tests `retry_backoff_is_bounded_and_wake_does_not_busy_loop`, `lifecycle_keeps_writes_during_request_and_pauses_work` in [client/connection.rs](../../../../../../crates/client/src/connection.rs); through the runtime, [sqlite/tests/runtime_lanes.rs](../../../../../../crates/sqlite/tests/runtime_lanes.rs) `the_push_lane_freezes_sends_settles_and_backs_off_with_one_shared_refresh` (a 200 to 300 ms timer after the first failure).
- **Pause abandons lane I/O without a report or a backoff, resume asks again, stop is final; close abandons a network call that never resolves and closed controls are inert.** Evidence: `pause_abandons_lane_io_without_backoff_resume_asks_again_and_stop_is_final`; the executors in [connection.test.mjs](../../../../../../integration/bindings/client-js/connection.test.mjs) `close aborts an uncooperative push and its late receipt never applies`, `closed connection controls cannot affect a replacement connection`, and [dart/test/connection_test.dart](../../../../../../packages/dart/test/connection_test.dart) `close aborts every effect its handlers still hold`.
- **The two lanes have independent lifecycle and retry state.** Evidence: `a_dropped_socket_backs_its_lane_off_while_the_push_lane_goes_on`, and the last step of `the_push_lane_freezes_sends_settles_and_backs_off_with_one_shared_refresh` (each lane backs off on its own schedule); the downlink lane's backoff, pause, resume and stop in [sqlite/tests/downlink_worker.rs](../../../../../../crates/sqlite/tests/downlink_worker.rs) `a_dropped_socket_reconnects_with_backoff_and_resubscribes`, `pause_ends_the_session_without_backoff_resume_reopens_and_stop_is_final`.
- **Concurrent 401s share one refresh, and a failed auth refresh is retried on the next attempt.** Evidence: `the_push_lane_freezes_sends_settles_and_backs_off_with_one_shared_refresh`; [live.test.mjs](../../../../../../integration/bindings/client-js/live.test.mjs) `client retries upgrade authentication and survives failed refresh`, `a 401 on both lanes at once shares one refreshAuth; both lanes recover with the new token`; [live_test.dart](../../../../../../packages/dart/test/live_test.dart) `native live client retries failed authentication refresh and closes without leaks`, `a 401 on both lanes at once shares one refreshAuth; both lanes recover with the new token`.
