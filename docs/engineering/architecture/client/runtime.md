# Runtime

## 1. Introduction and Goals

The runtime is the part of the client that owns a task from the moment an SDK submits it to the moment its outcome is delivered: it schedules local work on the one SQLite connection, holds the active application transaction, drives the connection lanes and direct calls, and decides when a result, a status or a change may be observed. Adding a language to AXTON means writing a carrier for JSON strings and adapters for the platform's network, timers and credentials, not a second copy of scheduling, retry, Query completion or Bootstrap rules ([#134](https://github.com/zanminwang/axton/issues/134)).

## 3. Context and Scope

An SDK sees four carrier calls and a wake:

```text
open(request, wake)        -> runtimeId; the open's outcome arrives as a taskCompleted
submit(runtimeId, message) -> admitted, or refused with client_closed when the runtime is gone
drain(runtimeId)           -> the events published so far, in order
detach(runtimeId)          -> no wake runs after this returns; the runtime is forgotten
wake(runtimeId)            -> "drain me"; carries no work
```

Admission is not completion. A submitted task is answered by exactly one `taskCompleted` event; the SDK resolves its Promise, Future or Completer from that event and from nothing else. An envelope that is JSON but not a valid input is admitted and answered with a protocol `report`; a command that does not decode still completes its request with the decoding error, so no waiter is left without an answer. The runtime asks for platform work as *effects* and hears their outcomes as *effect results*; an effect that is no longer wanted is cancelled, and a late result for a cancelled or unknown effect is ignored.

| Direction | Messages |
| --- | --- |
| SDK → runtime | `task {requestId, command}`, `transactionCommand {requestId, transactionId, scope?, command}`, `callbackResult {effectId, transactionId, ok, error?}`, `effectResult {effectId, outcome}`, `close` |
| runtime → SDK | `taskCompleted {requestId, ok, value, error?, details?}`, `effect {effectId, operation}`, `cancelEffect {effectId}`, `callCompleted {callId, outcome}`, `observerChanged {observerId, snapshot}`, `report {diagnostic}`, `runtimeClosed` |
| effect operations | `callback {transactionId, requestId}`, `http {route, body}` (`push`, `pull`, `action`), `socket {subscribe}` (a stream: `opened`, `message`, `overflow`, `closed`), `timer {millis}`, `refreshAuth`, `prerequisite {key, name, arguments}` |

Identities: `requestId` is the SDK's increasing counter, never reused; `effectId`, `transactionId`, savepoint `scope` and `observerId` are the runtime's, unique for its lifetime; `callId` is the durable call identity of the [protocol](../protocol/actions.md). Every identity travels as a string. The envelopes and the command set are the tagged types in [runtime/protocol.rs](../../../../crates/client/src/runtime/protocol.rs); [fixtures/bridge/envelopes.json](../../../../fixtures/bridge/envelopes.json) is decoded by the Rust, TypeScript and Dart tests alike. A failure the SDK maps to a public error carries a machine-readable `details.code` (`subscription.closed`, `bootstrap.superseded`, `client_closed`, a Bootstrap run's stored code); other failures are messages. The backend wire protocol is unchanged: the runtime prepares the same bytes the SDKs used to send.

Callers: the [bindings](../sdks/bindings.md), which run one runtime per open client on its own thread. Dependencies: the [frontend interface](frontend-interface.md) for every database operation, the [engine](engine/README.md) for what a receipt, page or response means, and the [connection](connection/README.md) state machines for when to talk to the server.

## 5. Building Block View

`ClientRuntime<S: ClientStore>` in [runtime/mod.rs](../../../../crates/client/src/runtime/mod.rs) is generic over the store and driven by three non-blocking calls: `receive(input, now, entropy)` admits one message and runs no database work; `step(now, entropy)` runs at most one local unit and says whether it did anything; `take_events()` hands over what the steps produced, in order. `now` and `entropy` are facts the caller supplies, so every scenario can be replayed deterministically.

| Module | Owns |
| --- | --- |
| [protocol.rs](../../../../crates/client/src/runtime/protocol.rs) | The envelopes, the command set and the diagnostic shapes |
| [tasks.rs](../../../../crates/client/src/runtime/tasks.rs) | Request routing, the ordinary FIFO, the admission-order scheduler, rebuild fencing and priority close |
| [transactions.rs](../../../../crates/client/src/runtime/transactions.rs) | The one open application transaction: its capability token, savepoint scopes, failure accounting and callback effect |
| [commands.rs](../../../../crates/client/src/runtime/commands.rs) | The local reads, writes, Scope, status and protocol-seam commands executed against the client |
| [effects.rs](../../../../crates/client/src/runtime/effects.rs) | The effect table, cancellation, the continuations effect results become, and the one shared credential refresh |
| [lanes.rs](../../../../crates/client/src/runtime/lanes.rs) | The connection intent and controls, the push lane over `ConnectionDriver` and `SyncCycle`, and the [Downlink worker](connection/controller/downlink-worker.md) driven as runtime work |
| [direct.rs](../../../../crates/client/src/runtime/direct.rs) | Direct Queries and Mutations, their deadline and refresh, and Query once flights |
| [prerequisites.rs](../../../../crates/client/src/runtime/prerequisites.rs) | The prerequisite loop: pick, run as an effect, record the outcome |
| [observers.rs](../../../../crates/client/src/runtime/observers.rs) | Subscription status, Bootstrap waiters and local watches |

The native side is [bindings/common/src/actor.rs](../../../../bindings/common/src/actor.rs): one thread per client owns the runtime and its SQLite connection, a mailbox admits messages, an outbox publishes events and wakes the carrier. The process-wide registry maps runtime ids to senders and outboxes and is locked only for that lookup ([Bindings](../sdks/bindings.md)).

## 6. Runtime View

**Scheduling.** Ordinary tasks form one FIFO. Inbound work - an effect result, a lane that became due - takes its place in the same arrival order: a lane unit runs when it was ready before the oldest queued task arrived, otherwise that task goes first, and after a lane unit the lane re-enters the order behind everything admitted so far. Neither foreground nor inbound work starves, and the order an application observes is the order things arrived in, as the SDK queues used to provide. One step holds at most one local transaction: a task, a transaction command, a commit or rollback, one Downlink pump (one page, plus the barrier settlement the [Downlink worker](connection/controller/downlink-worker.md#5-building-block-view) documents as its one exception), one receipt settlement, one direct-response application. The runtime never sleeps inside a step: a delay is a `timer` effect the host answers.

**Transactions.** A `transaction` task opens the session, issues a `transactionId` and asks for the application callback as an effect. From then on every ordinary task waits, reads included: none may see or join the open session. The callback's own commands arrive as `transactionCommand`s bearing the id and run on a continuation lane ahead of the parked queue. Nested savepoints keep a stack of runtime-issued `scope` tokens; a command names the innermost open scope or fails as a structural error, and `release` and `rollbackSavepoint` pop only the top. A failed command poisons the unit unless the savepoint it ran in rolls back. The `callbackResult` commits only when nothing is outstanding, no savepoint is open and no failure was recorded; otherwise it rolls back and the parent task fails with the first failure. A command that names a transaction that is not open fails with `transaction_closed`. The SDK keeps the callback's own return value and thrown value in language memory and settles with them once the runtime confirmed the commit or rollback; language-side async-context and zone guards still refuse a captured client from inside the callback, and the runtime's tokens enforce ownership even if a guard were bypassed.

**Network work holds no writer.** A direct call prepares its exact request, parks on an `http` effect and a deadline `timer`, and applies the response in a later unit; success is answered only after that commit, with the response's own outcome. A 401 asks for one `refreshAuth` effect, shared with the lanes, then re-sends the same body once under the same deadline. Stopping the connection fails a call still waiting on the network with `action.unavailable`, but a response already in hand is applied and answers its outcome; closing the client fails every call. Query once is decided here too: a saved result completes at once, a request for the same key is joined, otherwise one is fetched and every joined caller completes with its outcome. The push lane freezes a batch in one unit, sends it as an effect, and settles the receipt in another; `callCompleted` for a durable call follows the settlement commit. The Downlink worker's actions become effects - `open` a socket, `request` a pull, `wait` a timer - and its events come back from their results; its page queue, gap recovery, Bootstrap slot and fairness are unchanged. Every task or continuation that committed wakes both lanes.

**Observation after commit.** Subscription status is projected from the runtime's own connection state and published as `observerChanged` snapshots only when it differs from the last one; Bootstrap waiters settle on the committed transition of the run they registered with; a watch re-runs after every commit and publishes only a result that differs, never while a callback transaction is open. A watch whose first query fails is never registered: its task fails. A terminal snapshot (`closed: true`) ends a subscription observer on unsubscribe, rebuild and close, and a watch on close; `unwatch` ends a watch without one.

**Close and rebuild.** `close` is priority control: it rolls back an open session, cancels every effect, fails every queued and parked task with `client_closed`, ends every observer, and announces `runtimeClosed` only after the store is released, so the carrier may delete or reopen the files the moment it sees it. Durable accepted work stays in SQLite for reopen. A `rebuild` cancels every lane and direct effect (a direct call in flight fails with `action.execution_unknown`), resets the worker in place so it keeps its socket epoch and request allocators and the application's running or paused intent ([#162](https://github.com/zanminwang/axton/issues/162)), closes every subscription observer (the identities belong to the file left behind) and keeps the watches.

## 9. Architecture Decisions

**Rust owns the task, the host executes effects.** Putting all I/O in Rust would fix the platform boundary the SDKs need (Node's `fetch` and `ws`, Dart's `HttpClient`, the browser Worker of [#59](https://github.com/zanminwang/axton/issues/59)); leaving orchestration in each SDK duplicated every lifecycle rule. The runtime therefore requests effects and decides on their outcomes, and the host runs them.

**One actor per client, no process-wide execution lock.** A single actor would serialize independent clients; a lock held during database work or while waiting for a callback did the same. The registry lock covers map access only.

**No durable response inbox.** Task completions, effect replies and lifecycle control are lossless in memory; foreground memory stays proportional to outstanding callers, as the SDK promise queues were. Accepted user work is durable in SQLite already; a direct call's result was never stored.

**Admission order, not turns.** Alternating foreground and lane turns let an inbound page be applied ahead of an unsubscribe that had been requested before the page arrived. Arrival order is what the application can reason about.

## 11. Risks and Technical Debt

**Accepted limitation: foreground memory is proportional to outstanding callers.** The runtime never evicts an accepted task or a result; an application that submits faster than it drains grows its routes and the outbox, as it grew the SDK promise queues before. No public overload policy was added by [#134](https://github.com/zanminwang/axton/issues/134).

**Accepted limitation: watches re-run after every commit.** The runtime keeps the SDKs' coarse rule - any commit, including the push lane's own freeze, re-runs every watch and publishes only what changed. Dependency-aware notification is [#16](https://github.com/zanminwang/axton/issues/16).

**Not verified on a device.** The React Native carrier is exercised with the Node addon and the mobile transaction adapter; the Expo module is parse-checked and its Rust static library builds for the simulator target, but no simulator or device run is part of the repository gate ([platform smoke tests](../../../../integration/platform/README.md)).

**Follow-up.** The downlink hook of [#17](https://github.com/zanminwang/axton/issues/17) uses the callback-transaction seam established here; browser support ([#59](https://github.com/zanminwang/axton/issues/59)) reuses the runtime state machine behind a `postMessage` carrier.
