# Model and Action schema contracts — design (#141)

Status: approved design from [#141](https://github.com/zanminwang/axton/issues/141); implementation pending. This document specifies compiler and generated contracts. #145 must land before implementation; #142 supplies execution and #116 supplies Model Loader results.

## Context and ownership

The compiler currently parses `mutation Name { slot Model.operation }` into `Validated.mutations`, emits `mutations`/`clientPolicies` descriptors, and generates `client.mutate` for TypeScript and Dart. It does not parse ordinary Action inputs or outputs. The target is one `action` declaration and one backend capability with two explicit delivery contracts; this issue must not claim either new route runs before #142. Existing executable mutation behavior must remain usable during the compiler transition via an internal compatibility adapter or an implementation sequence that keeps the old path intact. No application-facing legacy migration promise is required.

## Schema and validation

`model` keeps stable identity, local CRUD and local get/query/watch. No `@local` or `@synced` distinction is introduced. `action Name(inputs)` has optional braces for named explicit outputs. Inputs include ordinary scalar/enum values and existing Model.create/update/delete operands with single, optional or list cardinality. An ordinary nullable input (`T?`) is a required argument key whose value may be null; omission is invalid. For `action Search(query String?)`, TypeScript requires `{query: string | null}`, Dart requires a named `required String? query`, and the backend `args` always contains `query` as string or null. Its descriptor carries `nullable: true` and `required: true`; there is no ordinary optional/absent argument syntax in this scope. An optional Model mutation operand (`Model.create?`, `Model.update?` or `Model.delete?`) may be omitted or null and is normalized to absent; its implied result is null. An omitted update patch field remains omitted, never converted to a null write. Retain restricted update fields, relation bindings, prerequisites, sequence and typed record references. Place declaration annotations such as `@version` and `@sequence` above declarations; member annotations remain beside members; Model `@@id` and `@@unique` remain inside.

Each create/update operand implies an output field of the same name whose value is the full authoritative Model resolved by its Loader, bound to the input identity. Each delete operand implies an identity-shaped confirmation, not a Model. An absent optional operand yields null; lists retain input order, count and duplicates. A named explicit output may be scalar, enum or Model, as required single, nullable single or non-null list of non-null elements. Nullable lists, nullable elements, nested lists, object/union shapes and streaming outputs are errors. Output fields are required even when nullable (present with null). An Action with no implicit or explicit output has a void result. An explicit output colliding with an implicit name is always an error; `call` is reserved in the Action namespace.

Implicit Model outputs take identity only from their corresponding input; handlers cannot redirect them. An explicit Model output handler returns an identity OBJECT, never a bare key or full Model. For `relatedTodo Todo?`, return `{ relatedTodo: { id: relatedTodoId } }` or `{ relatedTodo: null }`; the generated handler field is `TodoIdentity | null`, where `TodoIdentity` has the actual `@@id` fields. Composite identities are objects containing every key field, and Model lists return identity objects in input order. #142 implements the common identity validation and Loader resolver; duplicate Model types reuse that Loader. Successful delete confirmation asserts absence of the identity after execution and carries no stamp or old row. The returned Model is a stable Loader snapshot, including when later local optimism changes current `client.models` reads; repeated `wait()` on a live handle returns the same completed outcome without another load. This per-invocation snapshot is distinct from batch-final records used for settlement: final records cannot reconstruct an earlier call's result when a later call changed the same row. #142 implements the common Model loading/materialization path and carries each final call outcome through the backend transaction/receipt and ensures required local processing finishes before success. #116 retains per-output `@ephemeral` policy and dedicated mixed-output acceptance.

## Generated client and backend contracts

`client.models.<model>` offers local CRUD, get/query/watch; direct writes never enqueue. `tx.models` offers reads and CRUD only; watch and Actions are excluded. Standalone Model writes use a framework-managed local transaction. The default `client.actions.foo(args)` durably submits and returns `Promise<ActionCall<Output>>` after local commit; Model operands also apply optimism in that same internal transaction. `client.actions.call.foo(args)` is a separate request-response path returning `Promise<Output>` after remote execution and output processing, with no client queue or automatic optimism. Neither route is permitted inside an application-owned local transaction. Both use one generated input/output and one backend handler signature `{ ctx, args }`; `ctx` holds trusted framework context, and `args` holds client values. The backend remains application owned.

Shared `ActionCall<T>` exposes only `status: 'pending' | 'succeeded' | 'failed'` and `wait(): Promise<ActionOutcome<T>>`. TypeScript `ActionOutcome<T>` is `{ result: T; error: null } | { result: undefined; error: ActionError }`; successful void uses undefined. Initial local submission errors reject before a handle exists; terminal execution failure is returned by `wait`; direct call throws/rejects typed `ActionError`. A pending network retry remains pending. No handle result/error fields, subscriptions, progress or cross-Action transaction groups are added.

The flattened Model operands are `ModelCreate` (identity and fields), `ModelUpdate<K>` (identity plus selected optional patch fields) and `ModelDelete` (identity). Do not add public data/patch/op/identity wrappers around a whole operand. Preserve omitted update fields as omitted, not null. Existing scalar normalization, enums, identity, list encoding and typed references apply in TypeScript and Dart.

## Compiler/runtime seam

The compiler emits versioned Action descriptors for #142 and result identity/output descriptors for #116. Retain each Action version's input AND output contract, including the Model read-contract version used by each Model output. The generated backend handler types remain versioned, so an older Action handler continues to return the output shape and Model identity contract it declared. Each retained Model output selects the Model read version captured for that Action version, rather than silently using the newest Model shape; #142 and #116 use that versioned Loader contract. A changed or removed output, output cardinality or identity source requires a new Action version; same-version outputs use a conservative exact fence initially. An Action history file lives beside schema source and is reconciled before generated files are written. The backend stores each final call outcome atomically with business writes for idempotent replay; the client retains business results only in memory on a live call/handle, without a durable result-history API or restoration of old handles after restart. Durable pending work and completion/replay state remain engine-owned. Keep the current engine's `clientPolicies`, old parser branch and legacy generated mutation binding only as internal development compatibility while #142 converts the runtime; do not translate an ordinary Action into a fake Model mutation or expose a callable new route backed by a throwing placeholder. Export the new Action namespace and handle contracts as generated type-level interfaces until a real runtime binding is injected by #142. The existing `GeneratedClient` continues its working current path in this intermediate phase. #142 must wire the generated namespace into the public client and remove the temporary compatibility seam before claiming the Action API works. This staged boundary is a material review risk because the issue's generated contracts precede execution.

## Acceptance and limits

Compiler and generated type tests must verify syntax, diagnostics, cardinality, implicit and explicit identity sources, scalar/enum/Model/void mappings, `call` reservation, TS/Dart facades and backend `{ ctx, args }`. Regenerated fixtures and examples must label new calls as contract examples until #142 and #116 land. Update compiler and typed API architecture, schema reference and API index when shipped. #141 does not add `@tool`, invocation dependencies, old database migrations, direct-call retry policy or new execution-engine behavior. #142 owns queue/direct dispatch, lifecycle, error storage and reconciliation; #116 owns Loader snapshots and materialization. These ownerships are not completion gates on #141.
