# Bindings

## 1. Introduction and Goals

The bindings carry messages across the language boundary. In the client direction a binding is a carrier for the [client runtime](../client/runtime.md): it opens one runtime per client on a thread of its own, admits JSON envelopes, hands back the events the runtime published and wakes the SDK when there are some. It decides nothing and waits for no task, so a new language needs a carrier for strings and adapters for its network, timers and credentials, not a port of any logic ([#134](https://github.com/zanminwang/axton/issues/134)). In the other direction, the Node addon lets the Rust server call back into the application's transaction.

## 3. Context and Scope

**Client direction.** Every carrier offers the same four calls and a wake; the envelopes, identities and events they carry are the runtime's ([Runtime](../client/runtime.md#3-context-and-scope)).

| Call | Node (N-API) | Dart (C ABI) | iOS (C ABI) |
| --- | --- | --- | --- |
| Open | `runtimeOpen(request, wake)` → runtime id as a decimal string | `axton_runtime_open(request, wake, context, error_out)` → id, or 0 with `*error_out` | `axton_mobile_runtime_open`, the same shape |
| Admit | `runtimeSubmit(id, message)`; throws on refusal | `axton_runtime_submit(id, message, error_out)` → 0, or 1 with `*error_out` | `axton_mobile_runtime_submit` |
| Drain | `runtimeDrain(id)` → JSON array text | `axton_runtime_drain(id)` → JSON array, freed with `axton_free` | `axton_mobile_runtime_drain`, freed with `axton_mobile_free` |
| Detach | `runtimeDetach(id)` | `axton_runtime_detach(id)` | `axton_mobile_runtime_detach(id)` |
| Wake | `(runtimeId) => void`, a weak, non-blocking thread-safe function | `void wake(uint64_t runtime, void *context)`, called on a runtime thread | the same |

The open request is `{type: "open", requestId, path, schema, discardPending?}`. The call answers the runtime id at once; the open itself runs on the runtime's thread and completes `requestId` through the outbox with `{clientId, schema}`, or with the open error followed by `runtimeClosed`. `owner` and `migration` are accepted and ignored.

Admission is not completion. `submit` answers only whether the envelope reached the runtime's mailbox: it is refused with `client_closed` when the runtime is unknown, detached or closed, and at the boundary when the text is not JSON or a pointer is null. An envelope that is JSON but not a valid input is admitted and reported as a protocol `report`. Each task's outcome is its `taskCompleted` event. Runtime ids are allocated by the actor, never 0 and never reused in the process. The SDK Bridge is the only caller: [client-js/bridge.mts](../../../../packages/client-js/bridge.mts), which the React Native package reuses over its Expo module, and [dart/bridge.dart](../../../../packages/dart/lib/src/bridge.dart).

**Server direction** (Node only). `validateConfig`, `processPush`, `processPull`, `publish`, `negotiateLive`, `pullLive`, each taking the config JSON, the owner, the request, and a host callback `(requestJson) => Promise<responseJson>` that runs inside the application's database transaction ([Backend interface](../server/backend-interface.md)). `negotiateLive` also opens the socket's live session and answers `{handle, actions}`; two synchronous functions then drive it without a host callback: `liveEvent(handle, eventJson) → actionsJson` applies one event to the Rust `Subscriptions` controller and returns the actions the host executes, and `liveClose(handle)` forgets the session (idempotent). The session outlives each call in a process-wide registry keyed by the handle ([Server / Connection / Controller](../server/connection/controller.md)); the host's own transactions for `pullLive` stay outside the controller. A failure is a structured engine error `{code, message, details?}`: `code` is a stable machine name, `message` is for people and may be reworded, and `details` carries only the fields a code promises (`model_version_unsupported` on a pull or live subscribe has `model` and `version`). A push no longer answers `mutation_version_unsupported` or `model_version_unsupported` as a whole-request failure: each is a per-mutation rejection `{ordinal, code}` in the receipt instead ([#95](https://github.com/zanminwang/axton/issues/95)). An event on a handle that is not open, or one the session cannot accept, is `live.invalid_event`. The engine codes are declared in [server/error.rs](../../../../crates/server/src/error.rs); the host callback's own failures cross back as text and are filed under `host` with their message kept.

## 5. Building Block View

- **Runtime actor** ([actor.rs](../../../../bindings/common/src/actor.rs)). `open` allocates the id and registers the mailbox sender and the outbox before it spawns the thread (`axton-runtime-<id>`), so no wake can name an id the carrier does not know yet. The thread opens the store through `ClientRuntime::open_at`, then loops: admit every message already delivered, step until idle while yielding to new mail after every unit, publish what the steps produced, and block on the mailbox. It supplies the clock and entropy facts. A carrier that disappears without closing is detached by its platform's teardown hook - the Node addon registers an N-API environment cleanup hook per environment that detaches every runtime that environment still holds (a terminated worker included), the Dart Bridge attaches a `NativeFinalizer` calling `axton_runtime_finalize` to every runtime it opens (run when the bridge is collected or its isolate shuts down), and the Expo module detaches in `OnDestroy` - so an open SQLite transaction never outlives its carrier and no wake reaches a callback the platform has deleted; a panic inside the runtime is reported and closes it.
- **Registry.** One process-wide map from runtime id to mailbox sender and outbox. Its lock covers lookups and insertions only: it is never held during database work, while a callback transaction waits for the application, or while a wake runs, so independent clients never wait on one another.
- **Outbox and wake.** The outbox holds published events and a `wake_pending` flag under one lock, and the wake sink under a second one. Only the publish that finds the flag clear calls the sink; later publishes coalesce into that wake until a drain clears it.
- **C ABI** ([ffi.rs](../../../../bindings/common/src/ffi.rs)). Strings cross as NUL-terminated UTF-8: inputs are borrowed for the call, and every string returned (a drain batch, an `error_out` message) is allocated by Rust and freed exactly once with the carrier's free function. The `context` pointer is handed back to the wake verbatim and must stay valid until `detach` of that id returns. A panic never crosses the boundary. [bindings/dart](../../../../bindings/dart/src/lib.rs) and [bindings/mobile](../../../../bindings/mobile/src/lib.rs) export it under their own symbol names.
- **Node carrier** ([client.rs](../../../../bindings/node/src/client.rs)). Synchronous N-API functions over the actor. The wake is a thread-safe function called non-blocking, so the actor never waits on JavaScript, and weak, so an idle open client does not keep the process alive; the TypeScript Bridge holds a timer while a task or a close is outstanding instead. The server functions wrap a thread-safe JavaScript callback as the Rust host. The live session functions lock a process-wide registry (`LiveSessions`, handle → `Subscriptions`) only for the transition itself, since the controller is pure state. A server failure crosses N-API as the engine error's JSON in the rejection message, or in the thrown error's message for the synchronous functions; the server SDK's `typedNative` decodes it into `EngineError` (`code`, `message`, `details`) before any other code sees it. The transaction-bridge probe (`runProbe`) is compiled only with `cargo --features probe` into a separate `axton-node-probe.node`; the normal addon has no probe API.
- **Dart carrier.** [dart/bridge.dart](../../../../packages/dart/lib/src/bridge.dart) loads the library from `libraryPath` (or the process on iOS) and calls the C ABI on the calling isolate; no worker isolate remains. One `NativeCallable.listener` per isolate serves every runtime that isolate opens and is never closed, so no runtime can hold a pointer to a closed callable. The runtime thread calls it, it only posts to the isolate, and the drain runs on the isolate's event loop. The listener keeps the isolate alive only while an open, a task or a close is outstanding.
- **React Native carrier.** The Expo iOS module exposes `runtimeOpen`, `runtimeSubmit`, `runtimeDrain` and `runtimeDetach` as synchronous functions over the mobile C ABI; its wake posts an `axtonWake {runtimeId}` event on the main queue, and `OnDestroy` detaches every runtime it opened. [index.ts](../../../../packages/client-react-native/index.ts) routes that event to the shared TypeScript Bridge. Persistent database paths resolve under Application Support. [Module and build](../../../../packages/client-react-native/native-module/README.md).

Code: [bindings/common/src](../../../../bindings/common/src); [bindings/node/src](../../../../bindings/node/src); [bindings/dart/src/lib.rs](../../../../bindings/dart/src/lib.rs); [bindings/mobile/src/lib.rs](../../../../bindings/mobile/src/lib.rs) with the [Swift module](../../../../packages/client-react-native/native-module/ios/AxtonNativeModule.swift).

## 6. Runtime View

**Wake and drain.** Wakes are edge-triggered with a drain and recheck. The actor appends a batch and sets `wake_pending` under the events lock, then, outside that lock and under the sink lock, calls the sink if the flag was clear. `drain` takes the events and clears the flag under the events lock. The SDK Bridge drains until a drain comes back empty and dispatches in order; a wake that arrives while it dispatches is covered by that recheck. A publish that races a drain therefore lands in that drain or wakes again, and no event waits without a wake. A wake carries no work and never runs application code.

**Shutdown.** `close` is admitted like any envelope and runs as priority control: the runtime settles every task and ends every observer, the actor drops the runtime so the SQLite connection and its files are released, and only then publishes `runtimeClosed`. The SDK then rejects whatever it still routes and calls `detach`. `detach` takes the sink under the sink lock, which waits for a wake in flight, removes the registry entry and sends a close in case the thread still runs; once it returns no wake runs and none follows, so the carrier may free its wake context. After it, `submit` is refused with `client_closed` and `drain` answers nothing.

**Errors.** A client-direction failure is the `taskCompleted` message, plus a `details.code` where the runtime gives one; the SDKs map those codes to their public errors, and no status depends on the wording of the rest. Admission refusals are carrier errors (`client_closed`, or the JSON parser's message). Server-direction errors arrive as `EngineError`; the HTTP transport maps `code` to a status and everything else to `500 server` ([Server / Connection / Transport](../server/connection/transport.md)).

## 10. Quality Requirements

- **Every completion is delivered exactly once across drains, and a publish racing a drain never loses its wake.** Evidence: [bindings/common/tests/runtime.rs](../../../../bindings/common/tests/runtime.rs) `every_completion_is_delivered_exactly_once_across_repeated_drains`.
- **Independent clients make progress while one is parked in a callback or waits on the network: no lock is shared across them.** Evidence: `a_client_parked_in_a_callback_does_not_hold_up_another_client`, `a_client_waiting_on_the_network_holds_no_writer_and_no_other_client_waits`.
- **Detach stops wakes before it returns, rolls back and releases a live runtime, is safe from any thread and repeatedly; a lost environment detaches every runtime it held; `runtimeClosed` follows the release of the store; a failed open closes its runtime.** Evidence: `detach_stops_wakes_before_it_returns_and_closes_a_live_runtime`, `ffi_detach_is_safe_from_any_thread_repeatedly_and_for_unknown_ids`, `a_lost_carrier_detaches_every_runtime_it_still_held`, `open_answers_on_the_wake_and_a_failed_open_closes_the_runtime`.
- **Session isolation and closed handles behave as the session contract says, through the actor.** Evidence: `transaction_isolation_and_closed_handles_match_the_session_contract`.
- **The C ABI opens, wakes, drains, detaches and frees across the boundary, and refuses malformed input with the parser's message.** Evidence: [bindings/mobile/src/lib.rs](../../../../bindings/mobile/src/lib.rs) `runtime_carrier_opens_wakes_drains_and_detaches_across_the_c_boundary`, `a_failed_open_and_malformed_input_are_answered_across_the_c_boundary`; Dart exports the same [ffi.rs](../../../../bindings/common/src/ffi.rs) functions.
- **A Node process with an idle open client can exit; an outstanding task keeps it alive.** Evidence: [runtime-bridge.test.mjs](../../../../integration/bindings/client-js/runtime-bridge.test.mjs) `an idle open client does not keep the process alive`, `an outstanding task keeps the process alive until it settles`.
- **A failed Dart open leaves nothing attached: no SQLite sidecar or file stays behind, and the process exits on its own with no runtime keeping a wake registered and no listener keeping the isolate alive.** Evidence: [generated_test.dart](../../../../integration/generated-api/generated_test.dart) `a failed open leaves no runtime attached`, which runs [failed_open.dart](../../../../integration/generated-api/failed_open.dart).
- **An asynchronous host callback runs inside the application's transaction, and a broken transaction after a host write rolls both back** (server half of guarantee P6). Evidence: [transaction-bridge.test.mjs](../../../../integration/bindings/node/transaction-bridge.test.mjs) over the probe build; the production path is [runtime.test.mjs](../../../../integration/persistence/server/runtime.test.mjs) `a handler that breaks the transaction still fails the delivery`.
- **Server refusals cross the boundary as codes, and rewording a message changes neither the code nor the HTTP status.** Evidence: [server/tests/runtime.rs](../../../../crates/server/tests/runtime.rs) `push_refusals_carry_stable_codes_and_run_no_handler`, `malformed_requests_and_blank_owners_are_refused_with_codes`, `host_failures_keep_their_message_under_the_host_code`; [runtime.test.mjs](../../../../integration/persistence/server/runtime.test.mjs) `HTTP classifies native failures by code, not message wording; unknown codes fall back to 500`.

## 11. Risks and Technical Debt

**Accepted limitation: client-direction errors are messages plus codes where the runtime provides them.** A failure carries the engine's message and, for the registration, Bootstrap and close failures the SDKs map, a `details.code`. Other failures have no code; no SDK branch or status depends on their wording, and a typed client-side contract would need codes in `axton_core::Error` first.

**Resolved: one process-wide lock.** Node clients used to take one process-wide mutex for their SQLite work, and Dart isolates shared one global host, so clients in one process serialized ([#12](https://github.com/zanminwang/axton/issues/12)). Each client now runs on its own actor thread and the registry lock covers only map access; the evidence above shows one client progressing while another is parked in a callback or waits on the network. Measured on one host in debug builds through the public JavaScript client (200 direct round trips, 500 local transactions, a 2000-record Bootstrap, reads on one client while another is parked in a callback): every scenario stayed within run-to-run noise of the previous carrier, so no throughput change is claimed; the measurements are recorded in [#165](https://github.com/zanminwang/axton/pull/165). The server functions still re-parse and re-validate the config JSON on every call.

**Accepted limitation.** `open` accepts and ignores `owner` and `migration` ([#20](https://github.com/zanminwang/axton/issues/20)).
