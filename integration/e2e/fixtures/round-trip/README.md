# Round-trip fixture

The `Entry` / `Edit` schema, backend and console client behind [round-trip.test.mjs](../../round-trip.test.mjs), [subscriptions.test.mjs](../../subscriptions.test.mjs) and [bootstrap.test.mjs](../../bootstrap.test.mjs). It was the first public example; the public example is now [examples/todo](../../../../examples/todo/README.md). The fixture stays because its assertions (normalization, rejection, lost-response retry, offline reopen, catch-up, Node and Dart clients) and the generic `Entry` snippets in the [documentation](../../../../website/docs/backend/api.md) depend on it.

Besides `initialize`, `notify` and `listen`, the fixture exposes what a Scope's history needs to be arranged and inspected: `publishMany` (batched new rows, one cursor each), `publishOne` (one row on several channels), `republish` (a new position at the stamp the record already has), `tombstone` (a row deleted and published, so the Loader answers null), `failLoads`/`allowLoads` (a Loader that refuses named identities), `head` and `positionOf` (the channel head and a record's one retained position, read from PostgreSQL), and `reset` (an empty invalidation log, so a scenario's cursors are exact). Only the bootstrap scenarios use those; the other fixtures are unchanged.

`bash integration/e2e/run.sh` regenerates and installs it. `run.sh` here serves the backend alone for manual use of `client.mts` (`AXTON_URL`, `AXTON_DATABASE`, `edit TEXT`, `offline`, `online`, `status`, `quit`).
