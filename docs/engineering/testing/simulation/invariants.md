# Simulation invariants

Generated sequences explore combinations that named scenarios may miss. An invariant checks a required property at each step; assertions about convergence also need the scenario's subscription and delivery conditions to hold.

The [current checker](../../../../crates/sim/src/invariants.rs) covers stamps, cursors, duplicate execution, convergence when caught up, receipt agreement, completion only through a matching receipt, republication never advancing a stamp, and two stepwise checks: unsubscribing removes no content and reopening loses no pending operation. Read each predicate's conditions before claiming that it covers a guarantee.

```sh
cargo test -p axton-sim --test invariants --locked
```

The [runner](../../../../crates/sim/tests/invariants.rs) defaults to 60 seeds and 120 steps for its main random test. A longer exploration can use:

```sh
SIM_SEEDS=5000 SIM_STEPS=300 cargo test -p axton-sim --test invariants --locked
```

Both random tests run by default: `random_sequences_violate_no_invariant` with direct writes off and `random_sequences_with_direct_writes` with them on ([#33](https://github.com/zanminwang/axton/issues/33) fixed). Next review: examine whether the checker observes all relevant states without duplicating engine logic.

## Coverage review

Reviewed 2026-09-14 by reading [invariants.rs](../../../../crates/sim/src/invariants.rs), [step.rs](../../../../crates/sim/src/step.rs) and [sim.rs](../../../../crates/sim/src/sim.rs); table rewritten 2026-09-15 from the checker as it read while the simulation was being rewritten for [#55](https://github.com/zanminwang/axton/issues/55) (executed 2026-09-15: `cargo test -p axton-sim --locked` at the default size and `SIM_SEEDS=400 SIM_STEPS=200` on the invariants runner). The random runner subscribes every client to channel `a`, picks weighted actions (enqueue, freeze, pull, deliver, drop, duplicate, hold, swap, crash, restart, subscribe, unsubscribe, server change, membership move, reject-next, fail-next, fail-load-next, refuse-load-next, corrupt-next-page, and direct write when enabled; a pull covers every channel the client follows), settles every 25 steps, and checks the seven periodic predicates after every step; two more run at the step that can violate them. The default run is 60 seeds of 120 steps with three clients, once with direct writes off and once with them on.

| Predicate | Requirement it supports | What it actually checks | Limits |
| --- | --- | --- | --- |
| stamps never decrease | D2, D5, D6 | per client and record, the stored stamp never drops; the stamp row is retained across unsubscribe and deletion, so the high-water mark is never forgotten | A client with no row yet has nothing to compare. |
| cursors never decrease | A2 | per subscribed channel, the cursor never drops | Marks are forgotten for unsubscribed channels, because resubscribing legitimately restarts the cursor at 0. |
| no mutation executes twice | P1 | `(clientId, batchSequence, ordinal)` triples from committed pushes are distinct | Invocations from an aborted batch are rolled back with the host tables, so a P6 retry is not counted as a duplicate; correct, but it means the check says nothing about aborted attempts. |
| no pending means converged | D1, R1, A1 | a client with nothing pending, at a channel's head, holds the server's content for that channel's records | Exempts records a failed or refused read left stale until `settle` republishes them, direct-written keys until a change newer than the client's record stamp arrives (the client's own replacement rule, so a stale duplicate page does not lift the exemption), records whose membership left the channel, and channels whose own stamp is behind the content stamp. The runner asserts at least 1,000 comparisons across all seeds so the exemptions cannot silently empty the check. |
| receipts match server | P1, protocol | each receipt the client stored equals the server's stored receipt for that sequence | Only the latest sequence per client is retained on the host, so older receipts are not compared. |
| completed work had a matching response | A3, A5 | a frozen batch leaves the queue only through its receipt, and `last_completed_push` names exactly the highest batch that did so: a batch the server answered, never one it has not seen | Reads the queue and the completion counter; a batch the client never froze is not tracked. |
| republication cannot advance a stamp | D3 | on the server, every record's stamp equals the number of business changes committed to it, plus one if its first publication had to initialize missing metadata; publishing an existing record to a channel, however often, contributes nothing | Server side only; the client's view of the same rule is `stamps never decrease` plus convergence. |
| unsubscribe cannot remove content (stepwise, after `Unsubscribe`) | D6 | the snapshot of visible rows, stamps, before images and pending operations taken before the unsubscribe is unchanged after it | Runs only at that step; eviction is not a feature, so nothing is exempt. |
| a page moves a channel to its end or not at all (stepwise, on `Deliver`) | A2 | every channel cursor the applied page reports equals that channel's `to`, never a point inside the range | Checks the cursors the engine reports for the page as delivered, including duplicated and reordered copies; that a gap applies nothing is a named test ([Client tests](../components/client.md#pull)). |
| an unapplied change never changes local state (stepwise, on `Deliver`) | D7, D8 | a change reported `readFailed`, `skipped` or `conflict` leaves that record's stamp exactly as it was, and its content too, except for a comment removed because its parent entry was deleted by the same page | The cascade exemption was found by the random run at seed 9: a legitimate local cascade, not an engine defect. |
| no pending operation is lost on reopen (stepwise, after `Restart`) | L2, R3 | the queued ordinals and the completion counter `Crash` recorded are what the reopened client reports | A reopen is not a process kill ([Failure and recovery](recovery.md)). |

The former `claims belong to subscriptions`, `record rows have a claim`, `batches wait for their checkpoints` and `batches settle in sequence order` predicates are gone with the claims and checkpoints they read; the L4 case that `record rows have a claim` found ([#33](https://github.com/zanminwang/axton/issues/33)) is kept as a named scenario. A predicate that the random runner still lacks: a receipt's authority and a later page's authority for the same record agree at the same stamp on every client, whichever arrived first; the named scenario `reordered_receipt_and_page_agree_in_either_order` covers it.

Requirements with no invariant: P4 byte stability and L3 rollback scope. They rely on named scenarios. The unit tests in `invariants.rs` forge each violation behind the engine's back (deleting queue rows, forging the completion counter, regressing a stamp, erasing a pending operation from the SQLite file of a crashed client) and assert the report names it: `a_violated_invariant_is_reported`, `a_batch_gone_without_a_receipt_is_reported`, `a_forged_completion_counter_is_reported`, `a_regressed_stamp_is_reported`, `an_erased_pending_operation_is_reported_on_reopen`; `an_unsubscribe_retains_content_and_resubscribing_restarts_the_cursor` shows the retention check and the cursor restart, and `invariants_hold_through_a_plain_round_trip` the baseline.

Runs and results: `random_sequences_violate_no_invariant`, `random_sequences_with_direct_writes`, `publication_outside_membership_violates_no_invariant` and `every_run_ends_converged_after_settle` are the live checks. Verified 2026-09-14, before [#55](https://github.com/zanminwang/axton/issues/55): `cargo test -p axton-sim --locked --test invariants` passed at the default size and at `SIM_SEEDS=500 SIM_STEPS=200`. With the rewritten predicates: `cargo test -p axton-sim --locked` passed at the default size and the invariants runner passed at `SIM_SEEDS=400 SIM_STEPS=200` (193 s), both on 2026-09-15; no engine bug was found. After the pull protocol change ([#95](https://github.com/zanminwang/axton/issues/95)), executed 2026-09-16: `cargo test -p axton-sim --locked` (64 tests) and the invariants runner at `SIM_SEEDS=300 SIM_STEPS=200` (114 s); the one failure found was in the new checker, not the engine. The unit tests are what prove each predicate reports a violation. Membership faults (`generate_membership_faults`) are off by default and no test turns them on.
