# Downlink worker

## 1. Introduction and Goals

The Downlink worker owns everything the client receives: it follows the subscribed Scopes over one [live session](live-session.md) at a time, commits the first delivery boundary of every Scope still waiting for one, compares the acknowledged heads with the durable cursors, catches up over HTTP only when behind, then consumes the stream through a bounded in-memory queue. It belongs to the connected client rather than to a socket, so replacing the socket keeps its queue, its schedule and its durable position. HTTP fills gaps; the WebSocket carries only what is new. Every page, streamed or fetched, goes through the same gate in [Pull](../../engine/pull.md).

It owns a second, independent work class: the durable [Bootstrap](../../../protocol/pull.md) load of what a Scope published before its subscription's origin. One historical page is in flight across every Scope, beside - never instead of - the ordinary catch-up, and its completion barrier is settled by the delivery that reaches it ([#151](https://github.com/zanminwang/axton/issues/151)).

## 3. Context and Scope

The worker is a Rust state machine, `DownlinkWorker`, driven the way [scheduling](scheduling.md) and the [push lane](push-lane.md) are: the host feeds events and executes the actions Rust answers with. One binding command, `downlink`, carries both ([Bindings](../../../sdks/bindings.md)). The host owns the socket, the HTTP requests, the timers, its frame buffer and the credential refresh; it makes no sync decision.

Every event but `next` is **enqueued**: it reaches typed state and answers with no actions, so nothing is applied inside a transport callback. `next` is the **pump**: it consumes what is queued, commits at most one page, and answers with what to do next.

Events (`downlink {event, now, entropy, …}`):

| Event | Meaning |
| --- | --- |
| `start`, `stop`, `pause`, `resume`, `wake` | Lane controls, as for the push lane's `connection` command. |
| `next` | Pump once. The host loops on it while actions come back, and sleeps when they stop. |
| `message {epoch, body}` | A frame arrived on the socket of this epoch: the acknowledgement or a page. The host is the producer: it hands every frame over in arrival order and decides nothing. |
| `closed {epoch}` | The socket of this epoch closed. The host has already reported the error and refreshed credentials if it chose to. |
| `overflow {epoch}` | The host's frame buffer overflowed and frames were dropped before they reached the worker. |
| `response {request, body}` | The answer to the `request` action this id names. |
| `failed {request, reason?, status?}` | That request failed; the host has already reported it. `status` is the HTTP status when the host had one - for a historical page a refusal the server decided (4xx other than 401, 408, 429) fails its run, and anything else is retried. |

Actions, returned by the pump in order:

| Action | Host does |
| --- | --- |
| `open {epoch, subscribe}` | Open the socket and send the subscribe frame once it is open. Frames are `message` events of this epoch; the socket's end is `closed`. |
| `close {epoch, reason?}` | Close the socket of this epoch and abandon its request. A `reason` is a protocol violation to report as an error. |
| `request {request, body, bootstrap}` | `POST /sync/pull`; the answer is `response` of this id, a failure is `failed`. An ordinary catch-up (`bootstrap: false`) carries every subscribed channel and belongs to the open session, so the session's cancellation abandons it and its failure ends the session. A historical page (`bootstrap: true`) belongs to the lane: no session need be open, a replaced socket leaves it alone, its failure ends none, and only `pause`, `reset` and `close` abandon it. |
| `reset` | The replica under the lane was rebuilt: abandon the old socket, its catch-ups and the historical page in flight, and forget the old session, reporting none of it. It comes once, first in the pump after the rebuild and before any `open` or `request`, and replaces the `close` the old session would have had. |
| `bootstrap {scope, subscriptionId, state, run, cursor, barrier, error}` | A bootstrap run changed and the change is committed: `state` is the phase, `cursor` the historical progress B, `barrier` the fixed completion barrier H and `error` the stored failure. The SDKs publish it as the subscription's load status; no delivery decision depends on it. |
| `wake {lane: "push"}` | A page applied: wake the push lane so it re-evaluates what is eligible to send. |
| `report {reports}` | What a page could not apply (read failures, skipped changes, conflicts, divergences): deliver each to the application's `onError` as an `AxtonReport`. |
| `changed {scopes}` | A commit moved these Scopes' cursors, or committed their first delivery boundary: re-read their committed state for the subscription status the SDK publishes. |
| `acknowledged {scopes}` | The open session's handshake covered these Scopes: delivery for them is established, whether or not anything was committed for any of them. The SDKs read their `live` status from it; no sync decision depends on it. |
| `ledgerIssue {channel, message}` | A stored Bootstrap row of this Channel cannot be decoded, so the worker skips it (**Damaged ledger rows** below); `message` is the bounded reason. Deliver it to the application's `onError`: an `Error` in TypeScript and a `StateError` in Dart, whose message is `bootstrap ledger <channel>: <message>`. It is not a committed `bootstrap` transition and not a record `report`, so no status changes. |
| `wait {millis}` | Nothing to do until the timer fires; then pump again. One pump asks for at most one `wait`, and it is the earlier of the two schedules the lane holds - the socket's reconnect backoff and the bootstrap load's - so neither work class ever waits out the other's timer. A schedule that is due already asks for no `wait` at all when the pump gave the host something to do: the host pumps again as soon as the actions come back. |

## 5. Building Block View

Rust owns the snapshot of the channels, their subscription identities and the subscription generation, the first-boundary transaction, the catch-up loop, the rule that an acknowledged session catches up before trusting the stream, gap and overflow recovery, and the wake after an applied page.

- **Enqueue.** Lane controls reach the schedule at once; a frame is decoded and classified, an HTTP answer is matched to the request in flight. No database work happens here, and nothing the pump must see is dropped.
- **Pump.** Control work first, then streamed pages from the front, then the lane's next decision. At most one page application - one commit - per call, so foreground work, the push lane and later pages interleave; the host pumps again while actions come back.
- **The queues.** Streamed pages enter an in-memory queue bounded by `QUEUED_FRAMES` (64). Control work - the acknowledgement, an overflow, an HTTP answer - is queued apart from it and is never dropped for that bound; redundant overflows coalesce into the one recovery still to run. The consumer takes pages from the front through the gate: `applied` and `covered` pages leave the queue; a page with a gap on any channel **stays** at the front and one `request` runs from the durable cursors if none is in flight. Control work behind a held gap page still flows, so the answer that fills the gap is processed while the page waits. A page leaves the queue only by being applied or covered.
- **The bootstrap slot.** A second request slot beside the catch-up, holding the one historical page in flight across every Scope, the registration and run it belongs to, and the request its answer must be a page of. The two slots share one id space, so one test decides which work an answer belongs to; the slot names no socket epoch, so a replaced socket neither cancels nor restarts a load. A replaced replica does: a rebuild empties the slot (**Replica rebuild** below), and the fresh replica carries no load. Otherwise only `stop` empties it, and the durable task resumes on the next `start` without another call from the frontend. Its answer waits in a field of its own rather than in the session's control queue, which an ended session discards.
- **Bootstrap scheduling.** Every pump whose lane is started and not paused, and that has not already committed, asks the ledger for the next schedulable run and issues one `request` for `(B, S]`: the runs are enumerated in Scope order and the one after the last scheduled Scope takes its turn, so a Scope cannot starve another ([`Client::bootstrap_schedule`](../../../../../../crates/client/src/bootstrap.rs)). A run that is catching up has no page to ask for and is skipped. The read that picks the task is closed before the action leaves, so no transaction, lock or pump waits on the network. The enumeration is gated by the same wake the lane already gets after every commit, and a run whose subscription has no origin yet is not schedulable at all - which is why the transaction that commits a first boundary wakes the schedule itself ([`initialize_subscriptions`](../../../../../../crates/client/src/subscriptions.rs) in `acknowledged`): a load registered before its subscription had an origin starts on the next pump of the host loop that ran the handshake, rather than waiting for some unrelated commit.
- **Bootstrap answers.** A page is refused unless it answers the request that asked for it; then one transaction applies its authority and its progress together ([`Client::apply_bootstrap_page`](../../../../../../crates/client/src/bootstrap.rs)), and every test it makes is against what is committed now - so an answer that outlived its run, its registration or the lane writes nothing at all and announces nothing. A transport failure keeps the run and defers the same page on the lane's bounded backoff, with no overall timeout: waiting for connectivity is not a failure. That backoff is the load's own: the pages are paced by it and never by the socket's reconnect backoff, so a Scope keeps loading over HTTP while the socket cannot connect at all. A refusal the server decided, and an envelope that answers no request, fail the run until an explicit retry (`bootstrap.request_rejected`, `bootstrap.protocol_invalid`).
- **The completion barrier.** The terminal historical page fixes H, and the run completes only once `B = S` and `L >= H`. Committed delivery progress settles the barriers of the Scopes the commit announced, and a `start` re-evaluates every persisted barrier before any I/O, so a run whose delivery arrived while the client was closed completes without another request. This settlement is the **one exception to one commit per pump**: it runs in the same pump as the delivery commit that reached the barrier. It is bounded - one row per completed run, and the settleable Scopes are decided by one committed scan that binds at most 900 distinct names per query, so a barrier that is still short of its target opens no transaction at all - and deferring it would let a completion wait out a reconnect backoff, which is a worse trade than a second small write. Bootstrap never writes L and never fabricates progress: while `L < H` the ordinary catch-up path - a head above the cursor, acknowledged or streamed - is what advances it, and a run with nothing known above L simply waits for delivery.
- **Damaged ledger rows.** Every scan the worker makes of the Bootstrap ledger - the schedule, the reopen's barrier scan, and the settlement of the Channels a commit moved - decodes each row on its own. A row that cannot be decoded is skipped and kept exactly as stored: it is not reset, failed or completed, it supplies no completion evidence, and a named read of it (`bootstrap_state`, `request_bootstrap`, a page for it) still fails. Healthy runs keep their turn and their settlement beside it, and a schedule that finds nothing healthy clears its dirty flag as before, so it does not spin. The worker reports each skipped row once with `ledgerIssue`. It remembers the last reported defect per Channel as a fingerprint of the identity and the raw Bootstrap fields; a valid delivery cursor is left out, so ordinary delivery does not make the same defect new. A scan of every active row forgets a Channel it found healthy or absent, so a changed defect, or the same one coming back after a repair or a removal, is reported again; a settlement scan sees only its candidates and forgets nothing. The memory lasts the worker's lifetime and a rebuild clears it, so a new worker reports a defect once more on its first scan. A pump that fails drops its issues with its other actions, and it forgets that it reported them, so the next scan that finds them reports them again. Only a row's own decode failure is contained: an SQL, store or write error still fails the pump, and a value the store cannot hand over as JSON fails the whole read ([#163](https://github.com/zanminwang/axton/issues/163)).
- **Epoch and request id.** Every session has an epoch; socket events name theirs, so whatever an abandoned socket still delivers is ignored ([live session](live-session.md)). Catch-up answers are correlated by a worker-owned request id instead, so a held page cannot be confused with the repair it waits for and an answer to an abandoned request cannot end the session that replaced it. Both counters only grow for the worker's lifetime, a replica rebuild included, and stay within the safe integer range a JSON number carries: an exhausted counter fails the pump instead of wrapping onto an identifier already issued ([client/live.rs](../../../../../../crates/client/src/live.rs), `allocate`).
- **Subscription generation.** The engine counts committed subscribes and unsubscribes ([Frontend interface](../../frontend-interface.md), `subscription_generation`). A session records the value it started under; the first pump after a change ends it without backoff and starts one with the new channel set. The SDKs cancel nothing: `subscribe` and `unsubscribe` only write, then wake the lane, and the worker decides from the committed generation whether the membership actually changed - so an identical registration replaces no socket, and a rolled-back one reaches no session ([#150](https://github.com/zanminwang/axton/issues/150)).
- **Replica rebuild.** A successful `rebuild` command replaces the replica under a connected client in place ([Reconciliation](../../storage/reconciliation.md)), and the binding then resets the same worker (`DownlinkWorker::reset_for_rebuild`) instead of replacing it. The reset drops everything measured against the old file: the session, both queues, both request slots and any answer held for them, the retry backoff and the Bootstrap rotation. It keeps the application's intent - running, paused or stopped ([`ConnectionDriver::restart`](../../../../../../crates/client/src/connection.rs)) - and the epoch and request id counters, which are the fence against whatever the old replica's I/O still delivers; the fresh replica's subscription generation cannot be, because it may equal the old one's. A refused or failed rebuild leaves the worker untouched ([#162](https://github.com/zanminwang/axton/issues/162)).
- **Status.** The worker announces what the SDKs project a subscription's status from, and nothing more: `changed` for a commit, `acknowledged` for a handshake. The SDK adds the transport state its own lane holds - which session is open, how many catch-up requests are out, whether the lane is paused or gone - and builds no second network state machine ([client-js/subscriptions.mts](../../../../../../packages/client-js/subscriptions.mts), [dart/subscriptions.dart](../../../../../../packages/dart/lib/src/subscriptions.dart)).
- **Heads and initialization.** The acknowledgement carries each channel's head, and one local transaction turns it into durable state ([`Client::initialize_subscriptions`](../../../../../../crates/client/src/subscriptions.rs)). An acknowledgement that does not name exactly the Scopes the session subscribed is refused. A Scope whose stored subscription is no longer the identity the session snapshotted is stale work and is skipped. A Scope still waiting for its first boundary takes `starting_cursor = cursor = head`: a fresh subscription starts at the negotiated head and loads no history ([#150](https://github.com/zanminwang/axton/issues/150)). An initialized Scope keeps its cursor; a head below it is a reported server-state fault that ends the session and rewinds nothing. The transaction commits before any queued page is applied and before status is published, and the Scopes it initialized come back as one `changed` - so that pump holds that one commit and nothing else.
- **Catch-up.** Heads equal to the durable cursors mean no catch-up at all; otherwise one `request` from the cursors, repeated while any channel continues. Requests carry the initialized subscriptions only, while the subscribe frame carries every desired Scope, so a Scope waiting for its boundary is delivered to but never pulled from - a NULL cursor is never read as zero.
- **Recovery.** Overflow - the host's buffer or the page bound - discards the queue and recovers every channel from the durable cursor, because which frames were lost is unknown; the request in flight keeps its progress and another follows it, so sustained traffic cannot starve the catch-up that advances the durable cursor. The server's log is the durable queue and the cursor is the pointer into it.
- **Failures.** A socket close, a request failure, an unconfirmed acknowledgement, a page before the acknowledgement or a malformed frame ends the session; the lane retries with the [scheduling](scheduling.md) backoff. A subscription change, `pause` and `stop` end it without backoff. Whatever the ended session had queued is discarded: the next session recovers from the cursors.

## 6. Runtime View

1. The host loop asks for work, executes the socket, HTTP, timer and report actions without awaiting their answers inside the loop, and pumps again while actions come back. It sleeps only when the worker answered nothing (or `wait`) and no enqueue happened since the decision: every enqueue bumps a wake generation the loop re-checks before sleeping, so a wake between the two is never lost.
2. `start` or a `wake` on an idle lane snapshots the subscribed channels, their persistent subscription identities and the generation. With no channels the session ends successfully and the lane stays idle until a subscribe wakes it. Otherwise `open` carries the subscribe frame ([Protocol / Subscriptions](../../../protocol/subscriptions.md)) with the read contracts from the client's schema; catch-up requests carry the same declaration.
3. The first frame must be an acknowledgement for exactly the requested channels. Its heads are committed as the first boundary of every Scope that had none, that commit is announced with `changed`, and the acknowledged set with `acknowledged`; a refused acknowledgement announces neither. If every head then equals the durable cursor, the session is streaming at once; otherwise a `request` starts the catch-up and repeats while any channel continues. Frames that arrive meanwhile wait in the queue.
4. Each pump applies one page, wakes the push lane, announces the Scopes it moved and returns; the host pumps again for the next one. Reports from every applied page and answer come back as `report`. A commit that moved a Scope also settles a bootstrap barrier the move reached, in the same answer: waiting out a barrier writes nothing, so only the transaction that reaches it commits.
5. Bootstrap rides along: a pump that committed nothing applies the historical answer it holds, or asks for the next page of the run whose turn it is. A load and a delivery never share a commit, and a load never delays one - under sustained delivery a held answer waits for the first pump that commits nothing, which is self-correcting: the stream is bounded by what the server publishes, while the held page keeps its progress and its barrier meanwhile. A `pause` does not change this: no request starts, but an answer the host had already fetched is still applied, because it is local work whose records are stamp-idempotent.
6. The session ends with `close`: on a failure the answer also carries `wait`, and the next pump after it opens a new socket that subscribes again; on a subscription change the new session opens in the same answer; on `pause` or `stop` nothing follows.
7. After a replica rebuild the first pump answers `reset` before anything else, whether the lane is running, paused, stopped or has no Channel: the old host may still hold a historical page. A started lane, paused or not, then re-evaluates the persisted barriers, as on `start`, and an unpaused one opens a session for the carried Channels in the same answer; the next handshake commits their first boundaries at the acknowledged heads. A paused lane opens on `resume`, a stopped one only on an explicit `start`, and a lane with no Channel stays idle until a registration wakes it. Both SDKs wake the lane after the native `rebuild` command succeeds (the TypeScript `channels` event, the Dart `_channels` stream), so a lane asleep with no timer takes that pump without another `connect`; a failed rebuild wakes nothing. Old socket events and old answers of either HTTP class - already queued, arriving before the new handshake or after it, racing the abort - name an epoch or request id no current work holds and are dropped at enqueue. A pump that fails after taking the `reset` owes it to the next pump.

## 9. Architecture Decisions

### The downlink is a Rust state machine; hosts execute its actions ([#58](https://github.com/zanminwang/axton/issues/58))

**Decision.** The session logic that existed twice (`connect` in the TypeScript and Dart clients) is Rust, driven like `ConnectionDriver` and `SyncCycle`: the host feeds events, Rust answers with actions, and the host performs sockets, HTTP and timers. The server's per-scope drain policy is `Subscriptions` in `axton_server::live` ([Server / Connection / Controller](../../../server/connection/controller.md)). The connection model stays as chosen: HTTP writes, HTTP catch-up after the WebSocket acknowledgement, then live pages; no polling.

**Implemented contract.** Sections 3 and 5 describe it. It refines the contract this decision first sketched in four places, each chosen to keep the host without decisions:

- No `opened` or `subscriptionsChanged` event. `open` carries the frame, and Rust observes subscription changes itself through the engine's generation, so a host cannot forget to report one.
- No `acknowledged` event and no `apply` action. Every frame is a `message`; Rust tells an acknowledgement from a page ([Protocol / Subscriptions](../../../protocol/subscriptions.md)), applies pages itself, and answers `wake` when the push lane should run. The push lane's own `connection` command is unchanged.
- The lane's scheduling lives inside the worker (`start`, `pause`, `resume`, `wake`, `next`, `wait`), so a host drives one state machine per lane.
- Streamed frames are queued by Rust, bounded, rather than by the host; the host's buffer only bounds delivery. The acknowledgement's heads let a client that is already current skip catch-up entirely ([#95](https://github.com/zanminwang/axton/issues/95)).

**Consequences.** Both SDKs are transport code with no sync decisions; the transition tests run once in Rust. Dart's larger frame buffer and TypeScript's smaller one are host parameters ([Transport](../transport.md)); the worker's own bound is the same in both.

### Enqueue and pump are separate, and the worker outlives the socket ([#150](https://github.com/zanminwang/axton/issues/150))

**Decision.** Delivery is owned by a long-lived `DownlinkWorker`; `LiveSession` keeps only socket session state ([live session](live-session.md)). A transport callback enqueues a tagged event and wakes the host loop; only a pump reads or writes the database, and it commits at most one page per call. Control work is queued apart from the overflowable page queue, and catch-up answers are correlated by a worker-owned request id.

**Why.** Subscriptions become durable state with their own initialization, Bootstrap ([#151](https://github.com/zanminwang/axton/issues/151)) adds a second work class to the same worker, and both need an owner with a lifetime longer than one socket and a commit boundary the host can interleave with foreground work. Applying pages inside the frame callback gave the queue no owner, blocked repair answers behind a held gap page, and tied the lifetime of the queue to the socket.

**Consequences.** Enqueueing answers with no actions, so a host cannot act on a callback's return; `next` is the only command that commits, and the host loops on it. The lane's host loop is now a run loop with a wake generation, mirroring the uplink's. A burst that outruns the pump fills the page queue and recovers from the durable cursor - bounded extra work, one pull - instead of pacing the socket by the speed of commits.

**Validation.** Transition tests in [sqlite/tests/downlink_worker.rs](../../../../../../crates/sqlite/tests/downlink_worker.rs) and the binding tests in [bindings/common/tests/session.rs](../../../../../../bindings/common/tests/session.rs); the SDK integration tests for cancellation, overlap, reconnect and after-commit delivery assert observable behavior, and their fixtures now establish a catch-up the way a client meets one - a session initializes at the head it was acknowledged, the server publishes while the socket is closed, and the next handshake is above the committed cursor.

### A rebuild resets the worker in place ([#162](https://github.com/zanminwang/axton/issues/162))

**Decision.** After a successful rebuild the binding resets the connected client's worker in place and keeps its intent and its identifier counters; the host abandons the old I/O on the one-shot `reset` action, and both SDKs wake the lane. No second `start` is sent and no public API changes.

**Why.** Replacing the worker with a fresh one left a running lane stopped with no host command to restart it, and it restarted the epoch and request id counters, so a late frame or answer from the old replica could match new work with the same number. Sending `start` from each SDK would restore activity but not the fence; keeping the old queues would apply work measured against the old file.

**Consequences.** The fence stays local to the component that already owns correlation. The host learns about a rebuild only through `reset`, which it executes in batch order before the `open` that follows it.

## 11. Risks and Technical Debt

**Accepted limitation.** A gap page waits at the front of the queue until the pull that fills it returns; pages behind it wait too. Beyond 64 queued pages the worker recovers every channel instead. Correctness does not depend on the bound; only the number of catch-up requests does.

**Watch.** Because pages are no longer applied inside the frame callback, a burst that arrives faster than the pump commits reaches the bound sooner than it did and recovers from the cursor. The work is bounded - the queue is dropped and one pull runs - but the number of recoveries under sustained load is worth measuring before tuning the bound.
